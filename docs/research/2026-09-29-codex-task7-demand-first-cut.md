# Task 7 demand-first cut — adversarial code review

**Scope:** Read-only review of the draft Task 7 cut at `docs/plans/2026-09-21-care-and-justice-system.md:452-505` against the current code. No implementation or live Sheet read. `confirmed` means the cited code supports the statement; `contradicted` means the draft says something the code or its proposed mechanism cannot deliver; `risk` means the draft leaves a required behavior or proof unspecified. C109 live quantities and initiative row contents are claims in the plan, not independently verified here.

## Findings

1. **Contradicted — a failed demand phase does not necessarily stop Chaos Cars.** The draft says an unset `S.careJusticeDemand` makes the picker throw and thus fails *all ten* vehicle types for the Cycle (`docs/plans/2026-09-21-care-and-justice-system.md:472,480`). `safePhaseCall_` catches the demand-phase exception and proceeds to the next phase (`phase01-config/godWorldEngine2.js:159-169,322-329`). The proposed missing-demand check lives only in the demand-vehicle picker (`docs/plans/2026-09-21-care-and-justice-system.md:475-480`), while Chaos Cars selects and writes each event in sequence (`phase04-events/chaosCarsEngine.js:574-579,604-645`). A Cycle can draw only texture vehicles, or write texture events before its first demand vehicle throws. Later phases still run. If the intended invariant is zero chaos after a failed demand phase, it needs an unconditional check before the event loop (and a decision about already committed earlier-phase writes). An `Engine_Errors` row is conditional on that tab existing; otherwise the failure is only logged (`phase01-config/godWorldEngine2.js:103-130`).

2. **Contradicted — the 0.44 expected named cop-car contacts do not result from this cut.** The draft correctly says vehicle frequency remains 3–15 and only placement changes, but then says named contacts/arrests fall from about 0.62/0.093 to 0.44/0.066 *under this cut* (`docs/plans/2026-09-21-care-and-justice-system.md:476,490-491`). `pickEventCount_`, weighted vehicle choice, and uniform scope choice occur before target selection (`phase04-events/chaosCarsEngine.js:87-100,574-578`); cop-car has citizen and neighborhood scopes and 1.2 weight (`utilities/chaosCarsConfig.js:177-184`). Conditional on a citizen-scope cop-car event and any positive hood weight, the proposed two-stage picker *always* returns a tracked citizen. Normalizing `charges × trackedShare` across hoods changes **which** tracked citizen is hit, not the chance of a tracked hit. The sum of unnormalized weights, 0.44, is a proposed future frequency input, not this cut's expected event count. The draft's own Task 7b description at `:501,505` correctly places that frequency change later. This is a live-sim consequence, not merely wording.

3. **Contradicted — additional shared RNG draws move later outcomes.** The draft says a demand-vehicle citizen target uses two draws instead of one but “no other engine's draws move” (`docs/plans/2026-09-21-care-and-justice-system.md:479`). Chaos obtains `rng = ctx.rng` and draws targets, outcomes, magnitudes, and eight event-ID characters from that same stream (`phase04-events/chaosCarsEngine.js:61-65,137-145,562-563,574-619`). An extra target draw shifts subsequent Chaos Cars events, including texture vehicles, and the Phase-5 consumers of `ctx.rng` (`phase01-config/godWorldEngine2.js:329,338-368`; `phase05-citizens/runCivicElectionsv1.js:52`; `utilities/safeRand.js:28-35`). This is deterministic under the same code and seed, but not replay-equivalent across the code change. The proposed same-seed, same-code test at plan `:495` cannot prove the asserted unchanged downstream sequence.

4. **Contradicted — the demographics Sheet is already updated this Cycle before Phase 4.** The draft says “the sheet rows are last Cycle's close” for both source tables (`docs/plans/2026-09-21-care-and-justice-system.md:456`). Crime_Metrics writes are queued for Phase 10 (`phase03-population/updateCrimeMetrics.js:359-362`; `utilities/ensureCrimeMetrics.js:545-559`), so that description fits Crime_Metrics. Neighborhood_Demographics is different: its Phase-3 batch writer calls `setValues` directly before publishing `S.neighborhoodDemographics` (`phase03-population/updateNeighborhoodDemographics.js:324-334`; `utilities/ensureNeighborhoodDemographics.js:320-326,348-356`). Phase 4 therefore sees a same-Cycle demographics Sheet row. Reading `S` is still the right source for the proposed calculation, but the stated read-before rationale is factually wrong.

5. **Risk — the demand shape does not cover the census's disjoint `unallocated` scope.** The draft scales each raw hood-table population by `city / table sum` to compute `trackedShare`, while promising the census will keep raw `CoveredPopulation` and put the remainder in `unallocated` (`docs/plans/2026-09-21-care-and-justice-system.md:470,473`). The schema requires `unallocated` plus hood scopes and a derived city row (`docs/plans/2026-09-21-care-and-justice-system.md:218-240`); the arithmetic rejects a missing unallocated scope (`utilities/careJusticeAccounting.js:140-156`). `S.careJusticeDemand` contains only hoods and city totals, with no unallocated demand or explicit `zero/unavailable` status. The demographics table represents only a fraction of city population by design (`phase03-population/updateNeighborhoodDemographics.js:118-135`), and the proposed `hospitalIntakes` use *raw* hood `Sick` rather than a city-scaled count (`docs/plans/2026-09-21-care-and-justice-system.md:468,470`). Thus “city-scale 39 bed admissions” at `:493` is supported only as a sum for the hood table; Task 8 has no source for other-resident illness admissions in the city remainder. The rate-basis cancellation is valid for relative placement, but it does not reconcile citywide admission volume with census coverage.

6. **Risk — Task 8 needs typed hospital demand and movement state that the shape lacks.** The census has six hospital intake types plus `all` (`utilities/careJusticeAccounting.js:22-25,218-232`), and its `otherResident` input requires type, intakes, exits, transfers, corrections, and beds per disjoint scope (`utilities/careJusticeAccounting.js:113-126,194-212`). The draft shape supplies only one `hospitalIntakes` number per hood, no intake-type field, no `unallocated`, and no other-resident opening/closing or bed movement (`docs/plans/2026-09-21-care-and-justice-system.md:473,482`). It calls these illness-derived *bed admissions* (`:468,487`) but does not state whether they populate `illness`, `all`, or some other typed row. If Task 8 simply feeds intakes every Cycle, the census's other occupancy accumulates via `openingOther + otherIntakes + transfersIn − exits − transfersOut + corrections` (`utilities/careJusticeAccounting.js:236-255`); no 1–4 Cycle discharge or capacity behavior follows. The `40–80% full` forecast at plan `:487` is therefore unsupported by this cut. Census city totals themselves are summed from disjoint rows (`utilities/careJusticeAccounting.js:266-286,304-309`), so a missing scope cannot be repaired by a city-only number.

7. **Risk — floor-plus-flag overdraw cannot preserve both the modeled total and the census's intake identity.** The proposed helper returns `other = max(0, total − tracked)` and an `overdrawn` flag (`docs/plans/2026-09-21-care-and-justice-system.md:482`). If tracked exceeds the modeled total, `TrackedIntakes + OtherResidentIntakes` becomes tracked, not the modeled `judicialIntakes` or `hospitalIntakes`. The census sets `TotalIntakes` to that sum (`utilities/careJusticeAccounting.js:249-251`) and validates that identity, not equality to `S.careJusticeDemand` (`:342-345`). The flag is useful, but Task 8 must specify whether the demand total is revised upward, the cell is marked incomplete, or a correction is recorded. Without a persisted/checked link, a tracked spike can disappear from the demand-to-census comparison despite the returned flag.

8. **Risk — the existing weighted picker silently falls back to uniform when every weight is zero.** The draft requires a null target and friction instead of fallback (`docs/plans/2026-09-21-care-and-justice-system.md:478`). `weightedPickChaos_` currently returns a uniform item for `total <= 0` (`phase04-events/chaosCarsEngine.js:73-80`). A new demand picker must explicitly guard the weight sum before calling this helper, or OARI with no deployed hood and no-tracked-resident cases become uniform. The current `runChaosCarsEngine_` friction path does skip null targets (`:578-580`), so this is an implementation gate, not a reason to change that path.

9. **Risk — OARI deployment can silently flatten to zero unless tracker schema/state is validated.** The proposed lookup filters `PolicyDomain=safety` and phase in `{dispatch-live, operational}` (`docs/plans/2026-09-21-care-and-justice-system.md:469`), while the existing reader uses `findImplCol_` and substitutes blank values when columns are absent (`phase02-world-state/applyInitiativeImplementationEffects.js:219-224,406-413`). Its own delivery model recognizes additional positive phases, including `implementation-active`, `pilot-active`, and `complete` (`:315-325,330-346`). The narrower OARI phase rule may be intentional, but a missing/renamed column, changed phase, or tracker missing from `ctx.cache` would make every OARI weight zero if implemented as a blank list. The review cannot confirm the claimed live INIT-002 row from code. The build needs a fail-loud schema/read result and an explicit phase-transition rule before treating zero OARI hoods as a real absence of deployment. Doctrine §15 calls out gates whose inputs cannot reach them (`docs/SIM_DOCTRINE.md:125-140`).

10. **Risk — the 0.50 OARI diversion rate is config-weighted, but actual citizen outcomes are age-gated.** The config weights of the two `coverageContribution` outcomes sum to 0.50 in the current pool (`utilities/chaosCarsConfig.js:218-225`), confirming the draft's arithmetic for that unfiltered pool (`docs/plans/2026-09-21-care-and-justice-system.md:469`). Citizen-scope `substance_intervention` is barred for minors and `deescalated` for children under 13, however (`phase04-events/chaosCarsEngine.js:114-126,129-140`). The proposed citywide number is therefore a modeled adult-like rate, not the observed conditional probability for every named call. State whether it is deliberately independent of the tracked age mix.

11. **Risk — two-hood-set validation catches drift, but missing values can become zero before it.** Crime iterates the Neighborhood_Map set and publishes by-hood values (`phase03-population/updateCrimeMetrics.js:215-219,260-294,321-329`), while Neighborhood_Demographics loads sheet rows into a map and publishes them after update (`phase03-population/updateNeighborhoodDemographics.js:42-55,324-334`; `utilities/ensureNeighborhoodDemographics.js:134-171`). Comparing keys as proposed (`docs/plans/2026-09-21-care-and-justice-system.md:471`) is a valid drift guard. But the demographics reader converts blank/non-numeric `Sick`, `Students`, `Adults`, or `Seniors` to zero (`utilities/ensureNeighborhoodDemographics.js:163-171`). A matching hood with a malformed number can pass the key-set check and create zero demand or a zero population denominator. The new phase must validate numeric domains, finite totals, and nonzero table sum before calculating shares; merely checking missing `S.neighborhoodDemographics` does not do that.

12. **Confirmed — the proposed incident source and rounding boundary are the right ones, with a city-sum condition.** `calculateNeighborhoodCrime_` applies the cited weather, chaos, celebration, hotspot, nightlife, and traffic effects to `baseIncidents` before `trueIncidents` rounds (`phase03-population/updateCrimeMetrics.js:551-596,640-649`). The same `m.incidentCount` is queued for `Crime_Metrics.IncidentCount` (`utilities/ensureCrimeMetrics.js:374-383,507-559`), and `S.crimeMetrics.byNeighborhood` is available before Phase 4 at both entry points (`phase03-population/updateCrimeMetrics.js:321-329`; `phase01-config/godWorldEngine2.js:316-329,2030-2043`). The demographics publisher likewise precedes Phase 4 (`phase03-population/updateNeighborhoodDemographics.js:324-334`). The proposed *per-hood* rounding plus city sum of those rounded hood numbers at plan `:495` preserves city = sum of hoods. Rounding `sum(charges × clearance)` or `sum(sick) × admitRate` independently would not; the existing crime city `totalIncidents` already sums hood integers (`phase03-population/updateCrimeMetrics.js:694-724`). The quoted C109 totals require live evidence and were not code-verified.

13. **Confirmed — present target selection is uniform within its eligible pools; current OARI is not hood-gated.** `pickCitizenTarget_` excludes deceased, inactive, traded, and pending, then draws one eligible ledger row (`phase04-events/chaosCarsEngine.js:173-190`); `pickNeighborhoodTarget_` draws from Neighborhood_Map (`:267-293`). The vehicle config has the stated `cop_car`/`ambulance`/`oari_van` weights and two scopes each (`utilities/chaosCarsConfig.js:177-184,204-225`). The three weights total 3.1 of 8.7 across the ten non-episodic vehicles (`utilities/chaosCarsConfig.js:175-308,328-329`). The proposed tracked count must use exactly the status exclusion at `chaosCarsEngine.js:183-186` to match that pool. It still counts hospitalized citizens and minors, while a hospital intake requires an eligible status and an arrest is age/health-gated (`chaosCarsEngine.js:114-126,360-385,401-415`); `trackedShare` is exposure, not guaranteed intake probability.

14. **Risk — the bench plan cannot read the demand object from current cycle logs without an explicit diagnostic.** The draft says to read the 22-hood `S.careJusticeDemand` table from the cycle log (`docs/plans/2026-09-21-care-and-justice-system.md:499`). The planned cut writes no Sheet (`:464`), and the present engine's phase log serializes only timing fields (`phase01-config/godWorldEngine2.js:192-209`); `S.careJusticeDemand` has no reader or logger in current code (repository search returned only the draft plan). The build must specify a bounded diagnostic/log payload if that bench proof is required. Logging the object is a separate observable surface; absent that, a successful bench Cycle cannot verify the promised hood sums from the cited log.

## Review verdict

**Revise the cut before implementation.** The phase-order and per-hood source wiring are sound, and the OARI config probability is 0.50 for the unfiltered pool. The cut's claimed drop in named contacts, total-chaos failure behavior, unchanged downstream RNG sequence, and last-Cycle demographics Sheet state are contradicted. Task 8's unallocated scope, hospital type/movement inputs, and overdraw reconciliation need explicit contracts to make the census rows represent the claimed city demand.

**2026-09-29 (codex) — clarification to finding 2 and verdict:** The draft explicitly defers the 0.44 frequency to Task 7b (`docs/plans/2026-09-21-care-and-justice-system.md:501,505`); it does not unambiguously claim that this cut drops named contacts. The contradiction is the sentence that a tracked citizen is hit *as the sampled share of calls* (`:476`) and the “exposure as it stands” framing at `:490-491`: in this cut, a positive-weight citizen-scope event names a tracked citizen with probability one. Read the verdict's “claimed drop” phrase as that misleading exposure framing, not as a claim that Task 7b was included.
