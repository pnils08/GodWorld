# Codex adversarial cut review — engine.279

**Scope:** `docs/plans/2026-09-13-run-cycle-packages-the-world.md` §279 against the current source. Read-only code review; no cut implemented or bench fire run.

1. **HIGH — The late flush changes the failure boundary and can hide the original error.** The mint branch pushes a ledger row and writes `Generic_Citizens` before the pass clears intake rows; household formation also appends its two records before the proposed wrapper's `finally` would flush `LifeHistory_Log` (`phase05-citizens/processAdvancementIntake.js:924-976`, `:2212-2242`; `docs/plans/2026-09-13-run-cycle-packages-the-world.md:253`). Today an `appendRow` failure stops at that row, leaving earlier log rows durable and preventing later clears. With the proposed single write, a failure can leave **all** pass log rows absent after those other effects and queue clears; `safePhaseCall_` logs the failure but continues the Cycle (`phase01-config/godWorldEngine2.js:159-169`). If body and `finally` both throw, JavaScript propagates the `finally` error, so the originating row/operation disappears from the phase error. The claim that `finally` preserves today's mid-pass behavior is false for a failed flush. Require an explicit flush/error policy, preserve the primary error, and test both body-throw/flush-success and body-throw/flush-failure before clearing the queue. This cannot be described as behavior-identical without a ruling on partial writes.

2. **MEDIUM — `appendRow` and `getLastRow()+1` have different placement contracts.** The proposed write uses the last content row plus one (`docs/plans/2026-09-13-run-cycle-packages-the-world.md:253`); the existing writers use `appendRow` (`phase05-citizens/processAdvancementIntake.js:746`, `:936`, `:1982`, `:2241`, `:2358`). [Apps Script documents `appendRow` as appending to the current data region and `getLastRow` as the last row with content](https://developers.google.com/apps-script/reference/spreadsheet/sheet). A detached footer or formula below the log region can therefore change placement. A filter or frozen row alone does not prove such a difference, but neither is checked by the stub. `setValues` requires a rectangular range and interprets leading `=` as a formula; the present seven-element rows use the same Date/number/string values, so a typing difference is not established by this review ([Range reference](https://developers.google.com/apps-script/reference/spreadsheet/range)). Verify the actual log tail, grid row and column capacity, and one-row/multi-row placement on a copied tab before claiming exact equivalence.

3. **MEDIUM — The read-before omits other pass costs and overstates one log call per processed row.** A mint calls a full `Generic_Citizens` read and an `Emerged` cell write (`phase05-citizens/processAdvancementIntake.js:941`, `:2435-2449`); the cut removes the read but leaves the per-mint cell write. Each formed household also makes a header read and appends to `Household_Ledger` and `Family_Relationships` (`:2212-2234`). Contiguous intake clears can still make multiple calls (`:964-975`). Rows skipped for collision are cleared without a log append (`:685-699`), so the §279 phrase “per processed row: one append” is not literally true (`docs/plans/2026-09-13-run-cycle-packages-the-world.md:250`). Outside `processAdvancementRows_` but within `Phase5-Advancement`, the emergence, family and owner doors append queue rows individually (`phase05-citizens/processAdvancementIntake.js:1538`, `:1741`, `:1937`). This does not justify widening the two-day cut; it limits the performance claim and directs phase timing follow-up.

4. **MEDIUM — The held Generic snapshot is equivalent for this pass's own writes, with a concurrency limit.** Matching scans the first exact, case-insensitive name hit and does **not** filter on `Status` (`phase05-citizens/processAdvancementIntake.js:2438-2449`). After a same-name mint, `advNameIndex` turns the next plain queue row into an existing-citizen update, while a special door collision skips it (`:672-699`, `:926-927`); even if the marker is called again, an earlier `Emerged` status does not change which Generic row is first. The pass's own Generic writer changes only that status (`:2448`); household and owner helpers touch other tabs (`:1953-1982`, `:2176-2242`). Thus mirroring Status in the holder is harmless for current matching, but an external edit, insert or reorder between mints would be seen by today's repeated read and missed by a held row-index snapshot. State the no-concurrent-Generic-mutation assumption and test duplicate Generic names and a repeated mark; do not change name-matching or deduplication in this cut.

5. **MEDIUM — The proposed tests and bench equality gate miss the dangerous differences.** The current stub treats `appendRow` as an array push, has no grid size, and its `setValues` never throws (`scripts/householdIntake.test.js:36-49`); it cannot detect placement, capacity, partial-write, or masked-error behavior. The current test run is **39 passed, 0 failed**, so §279's “baseline 37” has drifted (`scripts/householdIntake.test.js:247`; `docs/plans/2026-09-13-run-cycle-packages-the-world.md:257`). Add injected log-write failure after ledger/Generic/household effects, dual body-and-flush failure, duplicate names, an already-Emerged first hit, and strict one-write/row-order/text/typed-cell assertions. The Cycle id seeds `ctx.rng` (`utilities/cycleModes.js:186-201`), but equal seed proves equal draws only when the **full pre-state, phase path, and draw offsets** match. The §279 old/new C110 comparison (`docs/plans/2026-09-13-run-cycle-packages-the-world.md:259`) needs a proven identical fresh resync, matching draw count and phase/error records, then exact relevant Sheet readback. Matching selected rows alone cannot establish equivalent execution.
