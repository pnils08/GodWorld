# Engine.334 plan review — mixed story seed magnitudes

**Verdict: HOLD.** The proposed `economic-event → sum` rule includes business closures, whose `-25/-40` values are fixed event impact scores, not economic ripple impacts. The plan itself lists closures as levels (`docs/plans/2026-11-05-story-seed-mixed-magnitudes.md:40`) while assigning the entire cause type to `sum` (`:52`). Reconcile the rule before Task 3. This is a plan review of `f6cd6c064`, not a review of a code change or a live Cycle.

## Findings

1. **High — `economic-event` contains two magnitude kinds.** A closure emits `causeType: 'economic-event'`, `effectType: 'business-closure'`, and `magnitude: -(25|40)`, copied from the world event's `impactScore` (`phase05-citizens/applyBusinessDynamics.js:685-700`). The economic ripple engine emits the same cause type with `magnitude: rlr.impact`, including births and carryovers (`phase06-analysis/economicRippleEngine.js:259-295`). Both phases precede the seed builder (`phase01-config/godWorldEngine2.js:642,697,760`), and that builder clusters by cause type plus hood, not source or effect (`phase07-evening-media/buildContractSeeds.js:466-476`). Thus a closure `-25` and an economic birth `+12` in one hood become one planned `sum` group: the closure leads and prints `business-closure -13`, while the cell says `-13`; neither number describes the closure or the economic impact. Two closures in one hood would print `business-closure -50` as if the fixed scores were additive. Use a grouping key that distinguishes closure level from economic ripple points, or give closure a separate cause type; retain the engine.206 carryover plus birth sum only within the economic ripple kind. Add both collision cases to Task 3. Existing 5b.a covers only two economic-ripple-engine rows (`phase07-evening-media/buildContractSeeds.test.js:198-213`), so it cannot catch this.

2. **Medium — the `What` reader inventory is too absolute.** The plan says no non-test reader parses `What`, and `/sift` matches on `Why`, not `What` (`docs/plans/2026-11-05-story-seed-mixed-magnitudes.md:46,91`). But `buildTransitSlice` filters serialized seed objects, which include `what`, by transit terms before taking four rows (`scripts/beatSliceKit.js:146-152`; `scripts/buildTransitSlice.js:201-205`). `/sift` explicitly permits a deck `What` / event-text match when citizens, entities, and `Why` do not match (`.claude/skills/sift/SKILL.md:254-255,450-455`). A changed `What` that adds or removes the only matching term can change which transit seed enters a slice or whether a candidate receives seed enrichment. Qualify the reader claim and include the text-filter and fallback-match paths in the Task 5 candidate review. The current plan's source-only scratch replay does not exercise those readers.

## Verified design implications and proof limits

- **Approval and economic carry:** each office-holder approval delta is added to each target hood's sentiment bus before its `approval-shift` ripple is emitted (`phase05-citizens/updateCivicApprovalRatings.js:1067-1103`); same-district office deltas are additive. `economicRippleEngine` emits one signed `impact` per birth or carryover (`phase06-analysis/economicRippleEngine.js:259-295`), and the existing test expects the carryover `4` plus birth `12` to print `+16` (`phase07-evening-media/buildContractSeeds.test.js:198-210`). That supports a *producer-scoped* sum, subject to finding 1. The unlisted `transit-event` game-day rows are per franchise (`phase02-world-state/updateTransitMetrics.js:639-664`); the physical game-day load takes the maximum when franchises share a hood (`:1079-1099`), so `level`/peak is consistent for that repeated effect. The static scan of 52 non-test call expressions established no other unlisted repeated same-effect case that must sum.
- **Replay scope:** `recordRipple_` queues the ledger row and then pushes the same event into `S.rippleEvents` (`utilities/rippleLedger.js:59-93`). The two engine entry points run the contract builder after the Phase 7 Famous ripples and before Phase 10 executes intents (`phase01-config/godWorldEngine2.js:742-760,835-870,2459-2477,2546-2568`); no Phase 8–10 ripple producer appeared in the source search. A successfully persisted ledger row has the builder's numeric and grouping inputs. A failed or omitted Phase 10 append can make the final ledger differ from what Phase 7 saw, so the proposed ledger replay is a saved-row comparison, not proof of every in-cycle seed. I did not rerun the plan's C110–C114 live counts or its projected 53 `What` changes and one class flip; no local Ripple_Ledger dump was present, and the draft replay script defaults to a Sheet read (`output/engine-sheet/2026-11-08-engine334-replay.js:51-57`).
- **Class can move both directions.** With two effects, `+0.03` and `+0.02` from unlike groups, the old total reaches the fractional `0.05` bar and the planned per-group rule does not (`phase07-evening-media/buildContractSeeds.js:121-126,524`; plan `:58`). Conversely, two same-cluster groups `+0.05` and `-0.05` currently total zero and are texture, but the planned any-group rule makes them major; positive and negative initiative intensities are valid producer outputs (`phase02-world-state/applyInitiativeImplementationEffects.js:565,688-708,752-765`). This promotion is consistent with the plan's stated rule, but Task 3 should test it and Task 4 should enumerate both directions. `Class` maps to next-Cycle priority 3/2 and is sorted before the 60-row carry cap (`phase09-digest/finalizeCycleState.js:732-768`), which Phase 2 weights (`phase02-world-state/applyCityDynamics.js:1036-1085`); major also sorts first in lives and gates the first three draft seeds (`scripts/buildLivesSlice.js:309-317`; `scripts/draftContentRows.js:281-290`), while `/sift` makes texture atmospheric only (`.claude/skills/sift/SKILL.md:257`). The C110–C114 one-flip estimate is therefore a finite historical sample, not a no-promotion guarantee.
- **Engine.332 boundary:** `coverage-reaction` clusters include `causeId` (`phase07-evening-media/buildContractSeeds.js:471-475`), each strong rating creates its own ripple (`phase02-world-state/applyEditionCoverageEffects.js:270-297`), and test 11l requires `+3` and `-3` to remain separate major rows (`phase07-evening-media/buildContractSeeds.test.js:414-418`). Keep this test and the exact `What`/rating assertions in §11/§12 unchanged through the build.
- **Weakest remaining assumption:** the cause-type unit table is too coarse because `economic-event` already crosses the proposed unit boundary (finding 1). The unit-blind `0.05`/`3` bar and blank-hood initiative merge are separate ranking and clustering decisions, respectively (`phase07-evening-media/buildContractSeeds.js:121-127,466-475`; `phase02-world-state/applyInitiativeImplementationEffects.js:752-765`). They can stay in the plan's open questions once the current cut preserves distinct units.
