# Task 7b cut — adversarial review

Review of commit `6751c50f`, `docs/plans/2026-09-21-care-and-justice-system.md:540-570`. This is a review of a proposed cut, not a diff review. `namedCallsField`, `careJusticeExposureDial`, `runChaosEvent_`, and the named pass are absent from the current code; the cited tests exercise Task 7. No engine code was changed for this review. Verdicts below say whether the **finding** is supported by the current code and contract.

1. **CONFIRMED — cop-car-only is a partial departure from the recorded three-vehicle ruling; it is technically separable.** The preceding Task 7 handoff says all three demand vehicles leave the 3–15 draw, and the builder question describes all three using one dial (`docs/plans/2026-09-21-care-and-justice-system.md:508,533-537`). Task 7b deliberately leaves ambulance and OARI in the loop (`:542,554-557`). The current picker routes all three through Task 7 placement (`phase04-events/chaosCarsEngine.js:608-612`); all three have citizen and neighborhood scopes (`utilities/chaosCarsConfig.js:177-189,204-231`). Keeping the loop selection for the two unmapped vehicles preserves their marginal selection and placement if the new conditional keys solely on `namedCallsField`. The rate choice for ambulance/OARI is genuinely open in this written cut; the builder should explicitly accept the partial delivery rather than treat the prior three-vehicle instruction as fulfilled. The last sentence at plan `:542` (later mapping is a config edit) is conditional on the pass being genuinely field-generic and using each vehicle's existing placement gates.

2. **CONFIRMED — loop thinning preserves draw weights, but contradicts the existing 3–15 *row* contract.** Today `pickEventCount_` yields 3–15 attempts, each attempt selects a weighted vehicle and uniform scope (`phase04-events/chaosCarsEngine.js:86-95,637-642`); `cop_car` has weight 1.2 and two scopes (`utilities/chaosCarsConfig.js:177-178`), and non-episodic weights total 8.7 (`:177-178,192,205,220,235,247,261,283,296,309,329-330`). Thus consumed cop/citizen slots average `9 × 1.2 / 8.7 × 1/2 = 0.621` per Cycle, while cop/neighborhood and other vehicle attempt probabilities remain unchanged. But a 3-attempt Cycle can now produce zero non-port rows if all three attempts are consumed and the pass names zero; a 15-attempt Cycle can produce more than 15 if the pass adds hits. The old acceptance is explicitly 3–15 **events**, not merely draws (`docs/plans/2026-05-07-chaos-cars-engine.md:38-44`), and the live validator counts non-port `Chaos_Cars` rows and fails outside `[3,15]` (`scripts/chaosCarsFrequencyCheck.js:19-39`). Task 7b's `:556,562,564,568` never reconciles this. Resolve the contract and validator together, or change the mechanism; do not call the old cap green after only checking `pickEventCount_`.

3. **CONTRADICTED — “one arrest per ~11 Cycles” is not a demonstrated receipt rate.** Task 7b multiplies the claimed 0.62 named contacts by the cop-car `arrested` weight 0.15 (`docs/plans/2026-09-21-care-and-justice-system.md:547-548`; `utilities/chaosCarsConfig.js:180-184`). The citizen outcome pool removes `arrested` for known minors before renormalizing the remaining weights (`phase04-events/chaosCarsEngine.js:108-135`), and an arrest outcome on a citizen in a health state emits a hook but no judicial receipt (`:452-473`). Hence 0.093/Cycle is at most the all-eligible outcome estimate; actual arrest outcomes and judicial intakes depend on the named residents' ages and states. The code cannot certify the quoted C109/C110 0.44/0.62 figures from the live inputs either: it only establishes the formula `trackedResidents / ratePopulation` and hood charges (`phase04-events/careJusticeService.js:191-210`). Label those figures as recorded bench observations and distinguish contacts, arrest outcomes, and judicial intakes in the rate test.

4. **CONFIRMED — the proposed inverse-CDF recurrence needs a numerical guard, not just `p_h = 1`.** The cut specifies `pmf(0)=(1-p)^n` and forward recurrence while allowing an uncapped dial and any `p_h` in `[0,1]` (`docs/plans/2026-09-21-care-and-justice-system.md:555,557`). For admissible `n=350,p=0.9`, `0.1^350` underflows to zero in JavaScript; multiplying that zero forward leaves the CDF zero although the binomial distribution is not concentrated at `k=n`. The current producer rounds `incidentCount` to an integer (`phase03-population/updateCrimeMetrics.js:640-649`), but the proposed pass checks only finite nonnegative `namedCallsField` (`docs/plans/2026-09-21-care-and-justice-system.md:554`); a malformed fractional count would silently cease to mean a binomial trial count. Require a nonnegative safe integer and use a numerically stable inversion (or fail loud when the calculation cannot represent the distribution). Test a high-`n`, high-`p` case as well as the stated small-`n` exact PMF and `p=1` cases (`:564`).

5. **CONTRADICTED — 22 RNG draws is a fixture count, not an invariant in the current service.** The intended unconditional draw, including `n=0`, `p=0`, and `p=1`, is a sound way to keep the pass's base draw count independent of outcomes (`docs/plans/2026-09-21-care-and-justice-system.md:557`). But `runCareJusticeDemand_` iterates `Object.keys(S.crimeMetrics.byNeighborhood)` and only checks equality with the demographics hood set; it never requires 22 hoods (`phase04-events/careJusticeService.js:154-181,191-212`). The synthetic fixture happens to create 22 (`scripts/careJusticeService.test.js:4-25`). Correct the contract to *one draw per mapped vehicle per demand hood*, with sorted keys; test draw count against `Object.keys(demand.hoods).length`. If precisely 22 is a required schema, add an explicit cardinality validation rather than relying on the fixture. A zero or one-probability branch must still call `rng()` once before returning its deterministic `k`.

6. **CONFIRMED — extraction can preserve the loop body, but the current tests do not establish “zero behaviour change.”** The existing loop owns both empty-target and empty-outcome friction with `event i` labels, then samples impacts, writes citizen state/intents, draws eight ID characters, writes the `Chaos_Cars` row, publishes receipts, and records ripples in that order (`phase04-events/chaosCarsEngine.js:641-754`; ID draw `:61-65`). The judicial receipt is deliberately after the source-row call (`:679-708`), while the citizen mutation precedes it (`:667-670`); `scripts/chaosCarsCitizenDial.test.js:159-198` and `scripts/judicialLifecycle.test.js:245-258` lock parts of this ordering. Moving only `:644-753` into `runChaosEvent_` requires an explicit return for the current `continue` at `:645`, and passing the original loop index label into the helper; otherwise friction, RNG, or side-effect order changes. Add an unmapped-vehicle forced-loop comparison of exact payloads, intents, hooks/ripples, friction, and RNG call count before/after extraction, plus a source-row throw test. The same-code determinism test at `phase04-events/chaosCarsEngine.test.js:91-111` cannot prove extraction equivalence.

7. **CONTRADICTED — “existing tests stay green with only `exposureDial` in the fixture” does not follow from the proposed code.** `scripts/judicialLifecycle.test.js:226-258` spreads the configured cop car into a forced citizen-only vehicle and asserts three loop rows and exactly 42 RNG draws. Once the config gains `namedCallsField`, those three forced loop slots are consumed by Task 7b; a 22-hood pass then changes both assertions. The proposed resident-index equality test also conflicts with `phase04-events/chaosCarsEngine.test.js:62-85`: its ledger has 40 eligible Fruitvale rows, while `makeDemandFixture_('Fruitvale')` says `trackedResidents: 1` (`scripts/careJusticeService.test.js:7-24`). The service harness's direct picker test has a second mismatch: its ledger has one eligible Temescal resident (`:53-73`), while that fixture reports zero Temescal residents (`:17-18,172-180`). Rebuild those synthetic fixtures from their ledgers or scope the index assertion to a self-consistent fixture, then update the forced cop test to assert thinning and pass behavior. The baseline four local tests passed before Task 7b: `careJusticeService` 16, `chaosCarsEngine` 52, `judicialLifecycle` 56, `chaosCarsCitizenDial` 27; those passes do not validate the proposed cut.

8. **CONFIRMED — the shared index must decide whether missing ledger columns fail loud.** All three current eligibility copies skip status filtering when `Status` is absent: `pickCitizenTarget_` (`phase04-events/chaosCarsEngine.js:173-190`), `pickCareJusticeTarget_` (`:313-327`), and `careJusticeTrackedByHood_` (`phase04-events/careJusticeService.js:114-132`). The target builder also emits an empty `popId` when `POPID` is missing (`phase04-events/chaosCarsEngine.js:194-223`), even though the event body uses it for source rows and judicial receipts (`:680-701`). Folding two copies into one helper while keeping those optional-column paths would silently count excluded residents or emit nameless citizen hits if a ledger header drifts. Add explicit `Status` and `POPID` header checks to the proposed index (or document and test the deliberate fallback); keep the texture picker's remaining semantics aligned with that decision. Task 7b's current proposed tests at plan `:564` cover missing demand fields, not missing ledger columns.

9. **CONFIRMED — bench acceptance must allow a valid zero or multi-hit result.** A mean of about 0.62 named contacts does not imply a single Cycle has only 0 or 1; the proposed binomial pass can yield two or more, and cop/neighborhood rows are random draws (`docs/plans/2026-09-21-care-and-justice-system.md:557,568`; `phase04-events/chaosCarsEngine.js:637-640`). Requiring a cop/neighborhood row “across the fires” as an acceptance gate can fail a correct short bench run by chance. The proposed always-present `careJusticeNamed` log (`:560`) and zero `Engine_Errors` are the deterministic path checks; rate evidence belongs in a synthetic distribution test with an independently computed expectation. The existing 3–15 validator conflict in finding 2 must also be resolved before treating bench row counts as passing.

**Evidence boundary.** C109/C110 live totals, named POPIDs, sandbox versions, and deployment state at plan `:544-548` are recorded observations, not derivable from these source files; this review did not contact Sheets or the sandbox. Current code does confirm the formulas and routing cited above. The current `weightedPickChaos_` still has a uniform fallback on zero total (`phase04-events/chaosCarsEngine.js:72-83`), and Task 7's demand picker correctly avoids it by checking total first (`:329-350`); the new named pass must likewise validate its own field and probability rather than coerce a bad value to zero or route through that fallback.
