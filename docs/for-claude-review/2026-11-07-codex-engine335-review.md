# Codex review — engine.335 household game-night fandom

**Target:** `3184f9f50` over recorded PROD stage 40: `phase05-citizens/runHouseholdEngine.js` and `utilities/citizenDialMap.js`, with the named plan and focused tests. The checked-out versions of these files match the commit.

**Result:** SHIP-WITH-FIXES — the writer and dial-map change match the builder's signed, one-step *input* ruling. Correct the two proof/reader claims below; neither calls for a code change to the candidate. Sandbox and PROD remain separate gates.

## Findings

1. **Medium — Acceptance 7 asks for a dial movement that one signed line cannot guarantee.** The plan says a signed live line means “that citizen's fandom moved by the line” (`docs/plans/2026-11-07-household-game-night-fandom.md:53-59`). The map does supply `fandom: ±1` (`utilities/citizenDialMap.js:96-102`), but Phase 9 nets all of the citizen's same-Cycle effects before applying them (`utilities/compressLifeHistory.js:1632-1648`), and `roomScaled_` reduces a push near its pole to zero at 0/100 (`utilities/citizenMemory.js:79-99,108-115`). A lone +1 household line at fandom 100 produces no numeric movement; an opposing −1 line in the same Cycle nets to zero. A lone line at 80 adds 0.4 to current fandom, not 1. `settleCycle_` decays fandom mood by 0.9 on later folds (`citizenMemory.js:37-42,204-210`); `TraitProfile` reads *base*, while the one-off lands in `DialState.mood` (`utilities/compressLifeHistory.js:708-718,1703-1715`). Consumer bands change only at thresholds 20/40/60/80 (`citizenMemory.js:53-58,213-221`), so even current 50→51 has no immediate band effect. Thus an exact +1/−1 `TraitProfile` or before/after value check can reject a correct live fire or claim proof from the wrong cell. State the ±1 resolver input as the acceptance contract and evaluate the live `DialState` transition against its other Cycle lines, current-value room, and settle step. Treat `TraitProfile` as a base/band read, not the per-line receipt.
2. **Low — Design 4 overstates two downstream readers.** The plan says resonance recall and backdate gain fandom from signed household tags (`docs/plans/2026-11-07-household-game-night-fandom.md:38`). Resonance recall calls `nudgesForEvent_` only on a reflection's `meta.affect`, not on a LifeHistory event tag (`lib/resonanceRecall.js:71-76,90-95`), so a signed household line alone leaves its recall score unchanged. `backdateCitizenDials.js` sums the new tag during `backdate()` (`:64-74`), but its normal rebuild path then calls `carryFandom_` (`:148-154`), which replaces calculated fandom with existing `DialState.base.fandom` when present (`:56-61`). Therefore a rebuild of an existing citizen does not gain that historical signed-line fandom. Correct the reader inventory; the live Phase-9 fold is unaffected. `seedTier1Essence.js:31-40` would route such a tag if one were supplied, but its fixed essence data does not currently emit one.

## Source trace and reader audit

- Both engine entry points run the household writer before citizen events and the Phase-9 compressor (`phase01-config/godWorldEngine2.js:646,657,810,2366,2377,2522`). The household and city fan writers select the first supported played club's feed row, then call the same `gameNightBucket_` with that club's `sportsWeek.hotCold` (`phase05-citizens/runHouseholdEngine.js:409-421`; `generateCitizensEvents.js:2173-2192`; `applyGameNightMoments.js:103-112`). Each maps `win`/`winStreak` positive and `loss`/`coldStreak` negative; neutral stays unsigned (`runHouseholdEngine.js:431-435`; `generateCitizensEvents.js:2193-2199`). The picked household line adds the chosen tag to in-memory LifeHistory and `S.householdEvents`, and queues a `LifeHistory_Log` append (`runHouseholdEngine.js:569-617`). No new global function or variable is introduced: `gameNightTag` is local to the writer; the other changes are map keys.
- `baseTag_` removes only a terminal calendar suffix. It strips the old/plain `Household-GameNight` to `Household`, but leaves `-GameNight-Win` and `-GameNight-Loss` intact; `nudgesForEvent_` then resolves the two exact keys to `{family:5,fandom:±1}` (`utilities/citizenDialMap.js:97-102,303-306,341-353,370-389`). The LifeHistory parser accepts the full signed bracket tag (`utilities/compressLifeHistory.js:821-839`). Older stamped lines already below the fold watermark do not re-fold; legacy plain lines still resolve to family only (`utilities/compressLifeHistory.js:542-565,1609-1621`). The graded-tag route would carry only fandom (`citizenDialMap.js:308-329,370-377`), so the direct map entries preserve family.
- Live consumers change as intended: `foldNewEntries_`/legacy `foldOneEntry_` receive the new map (`utilities/compressLifeHistory.js:1632-1657`), and wake `recentEventMagnitude` scores a signed line at total magnitude 6 rather than the old plain line's 5 (`lib/wakePerception.js:31-45`). `deadBranchScan` calls the resolver and treats both new tags as non-inert (`scripts/deadBranchScan.js:214-223,268-277`). The signed raw tag can appear as a distinct `TopTags` token when a face is recomputed (`utilities/compressLifeHistory.js:1716-1724`); the citizen-event continuity comparison is exact against its own `recentPrimary`/pool tags (`phase05-citizens/generateCitizensEvents.js:763-769,3486-3501`), with no demonstrated wrong draw from this change.
- No wrong downstream retag was found: the pulse map has no Household key (`utilities/neighborhoodPulseMap.js:22-69,96-114`); Who Lived It and the Saturday audit require exact `Household`, so both already excluded the old game-night tag (`scripts/buildWorldSummary.js:301-312`; `scripts/cron-saturday-run.js:1073,1129`); Lives slice accepts either suffix via its `^Household(?=$|-)` rule (`scripts/buildLivesSlice.js:52-56,340-346`); `TAG_TRAIT_MAP` has no game-night key (`utilities/compressLifeHistory.js:175,251-255`). The game-night Ripple still collects the picked POPIDs and emits the same cause, effect, targets and magnitude (`phase05-citizens/runHouseholdEngine.js:584-586,634-648`). No production reader found interprets a terminal `-Win` or `-Loss` as a separate instruction. Offline classifier exact scoring uses `baseTag_` (`scripts/classifierGate.js:99-101`), but its fixed truth cases do not supply these tags.
