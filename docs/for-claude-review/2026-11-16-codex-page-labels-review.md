# Page labels off citizens' memory plan review

Reviewed `docs/plans/2026-11-16-page-labels-off-citizens-memory.md` against current source. No code was edited and no live store or Sheet was read.

1. **High — writer inventory is incomplete.** `scripts/maraMemory.js:84-93` writes directly to `/v3/documents` with `[PARENT, CONTAINER]` tags and caller-supplied `content`; it bypasses `appendReflection_` and can write labelled desk records to `citizen-pages`. Its current caller/content contract must be checked and included or explicitly ruled out. The named `appendReflection_` call sites are not the only write route: `scripts/cron-desk-writer.js:890-895` uses the helper for a note, while `scripts/cron-desk-run.js:3454-3461,3663` routes `filed:` / `graded:` through `citizenVoice`; `scripts/cron-civic-run.js:3764` passes a prefixed datawake to `officeWall`. Add direct-writer audit and make the writer table distinguish raw append callers from label-producing call sites.

2. **High — reader inventory and “no reader parses” claim are incomplete.** `scripts/buildLivesSlice.js:79-95` sends admitted pages through `scanCitizenPages.citizenText`; `scripts/scanCitizenPages.js:131-138` strips `TENSION[...]` and `TENSION-RESOLVED[...]` prefixes. That is an active reader transformation and must be migrated or shown unnecessary. `scripts/buildCitizenWeekDigest.js:298-310` explicitly excludes leading `filed:` / `graded:` rows. `scripts/officeWall.js:88-94` also falls back to matching `stated:` / `datawake:` although its writer sets `daypart: CIVIC`; changing the writer alone alters the fallback for old documents. The plan should enumerate these readers and define compatibility for old records. The stated claim that no reader parses these labels is therefore false as written.

3. **High — dial assertion misses classifier inputs and the reporter-grade path.** The `Reflection_Intake` rows store event/affect tags rather than reading pages (`scripts/citizen-wake.js:605-615`; `scripts/cron-work-wake.js:495-500`), and tension state is independently persisted (`scripts/citizen-wake.js:575-598`). But page labels do reach classifiers: `scripts/citizenVoice.js:233-251` classifies `said.spoken` before appending, and marks grade based on `preText` at :241; `scripts/cron-work-wake.js:473-480` classifies the generated reflection; citizen wake classifies its reflection at `scripts/citizen-wake.js:521-532`. The plan already flags reporter grade text, but should trace each route and separate page text from separately supplied labels/grade metadata. Removing prefixes from text could change classification, and Task 3's “builder's call” should be resolved before Task 2 changes that path.

4. **High — readers-first is not safe for a mixed live week as specified.** Task 1 changes `lastGradedLine` to metadata, but Task 2 is when new writes begin carrying the score in metadata. Between those deployments, a reader that relies on metadata will miss newly written grades from the still-old writer; after writer deployment, new format can coexist with old label-only docs and readers must support both. `scripts/cron-desk-run.js:1534-1539` currently reads the content label, while `scripts/citizenVoice.js:244-251` writes only `affect`, `event`, and `ask` metadata. Define a staged dual-read/dual-write transition (and deployment order) so either intermediate version can read both formats, then retire fallback only after old entries age out or are migrated.

5. **Critical — bulk rewrite can corrupt same-customId append history.** `lib/citizenPage.js:41-42,77-82` documents that POSTing a repeated customId appends content to the existing document rather than replacing it. Task 4's rewrite must not POST cleaned content under the existing customId: it would append a second variant, leaving the old label in place and potentially duplicating history. It also must preserve keys: `lib/citizenPage.js:152-156` constructs the customId, and customIds are consumed as identifiers (for example `scripts/citizenVoice.js:242-250` distinguishes grade docs by key; `scripts/cron-desk-run.js:1534-1537` filters grade documents by suffix). Specify an update/replace operation with verified readback, or a new versioned ID plus migration of every keyed consumer; preserve the original snapshot and make reruns idempotent. Do not count metadata-only changes as a rewrite until the store's supported update semantics are established.

6. **Medium — the proposed `stated:` / `datawake:` metadata replacement needs exact type/key mapping.** `scripts/officeWall.js:149-160` writes `kind`, `office`, and `holder`, but its cascade/datawake constructors at :168-200 encode topic, statement, action and signal in the content and key. Task 2's metadata list (`kind`, `cycle`, `topic`, `score`) does not account for these fields or guarantee a unique `customId` when multiple statement lines share a cycle. Define metadata and key semantics that retain wall ordering/content and avoid collisions; retain a legacy-label fallback during migration.

**Verdict: HOLD.** Resolve the incomplete readers/writers, staged compatibility, classifier decision, and store replacement semantics before implementation. Source review only; no tests, live Supermemory reads, Sheet reads, or migration behavior were run.
