## Findings

1. **[Medium, confirmed] The pack can reject a delivery edge the engine accepts after a target-list edit.** `scripts/civicStageEvidence.js:58-60` resolves the *current* `AffectedNeighborhoods` for every audit Cycle and requires it to equal the baseline's frozen keys. `lib/initiativePhaseContract.js:657-684` and its engine mirror `phase05-citizens/civicInitiativeEngine.js:4424-4429` judge only those frozen keys. Failing input: a valid transit baseline frozen for `Downtown` at C109, a C110 Downtown station lift, and the row subsequently changed to `AffectedNeighborhoods: Downtown,Fruitvale`. A local reproduction gave `deliveryEdge: {available:true,minEdge:1.6}` while `measureStageMovement` gave `{available:false,reason:"target cohort changed/unknown"}`. The board therefore reports no measurable movement while the engine can count the observation toward Delivering. Choose one contract for edits after baseline and enforce it in both readers; if the baseline owns membership, the pack should read its frozen keys. The current tests keep the row target unchanged (`scripts/civic47Transit.test.js:38-60`). This was in the original patch and remains after the fold.

2. **[Medium, confirmed] A malformed baseline can reverse the pack/engine movement verdict, and missing city membership is accepted.** `scripts/civicStageEvidence.js:28-31` checks tab, scope and columns against the catalog but does not check `baseline.direction`; it computes with `metric.direction` at `scripts/civicStageEvidence.js:91-96`. `lib/initiativePhaseContract.js:645-647,684-688` instead accepts either stored direction and scores with `baseline.direction`. Failing input: take an otherwise engine-built C109 transit baseline for Downtown, change only its stored direction to `down`, then lift Downtown stations at C110. Local reproduction: engine edge `-1.6`, pack `available:true, metricMoved:true` with difference `+1.6`. Additionally, `lib/initiativePhaseContract.js:655-656` and `scripts/civicStageEvidence.js:83-84` check `cityN` and `city` only if present; deleting both from a v1 descriptor leaves both readers available despite no frozen city membership. `scripts/civic47Transit.test.js:38-48` actually builds and accepts that incomplete descriptor, so its positive result cannot prove the new membership guard. Validate the baseline descriptor's required fields and direction at the read boundary, with explicit handling for any genuinely supported legacy descriptor.

3. **[Medium, confirmed for a partially seeded canon context] Freeze can throw before publishing an unavailable cohort.** `phase05-citizens/civicInitiativeEngine.js:4260-4267` checks only `canonHoods.list`, then transit calls `resolveHoodOrChild_` at `:4274`. The real resolver throws unless `.set` and `.children` exist (`phase01-config/canonNeighborhoodLoader.js:441-445`); the later baseline writer already knows to guard both (`phase05-citizens/civicInitiativeEngine.js:4363-4365`). Failing input: staged transit row, valid C109 station grid, `ctx.summary.canonHoods={list:['Downtown']}`. A local execution with the real resolver threw `canonical hood set not seeded` and left `civicStageCohort:null`, rather than naming the transit tab unavailable. `lib/initiativePhaseContract.test.js:291-307,698-700` injects a resolver that ignores this incomplete context, so its new freeze test passes without covering the real failure. Guard the complete canon shape before either tab reader runs. This is a failure-path hardening issue; the normal loader's full seed was not shown to produce a partial object.
