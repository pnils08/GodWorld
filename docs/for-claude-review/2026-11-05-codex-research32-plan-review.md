# research.32 plan review — Discord voices lookups

**Verdict: HOLD the plan for a fold before the build.** `tool_choice: any` still forces at least one tool use, but the current bot would send every new lookup to `searchEverything(undefined)`. The proposed table reads also conflate current counts with events, the GAME-mode character list with a club roster, and card update time with in-world Cycle. These are plan findings, not a review of an implementation candidate.

Scope: `docs/plans/2026-11-05-discord-voices-lookups.md` as reread on 2026-11-05, including the added `Team Record`/`Streak`/`WeekRecord` line; the named bot and library code; local C113/C114 snapshot shapes and their producers/consumers. No Sheet, Discord, model search, bot restart, or live Cycle was used for the findings.

## Findings

- **F1 — HOLD, tool dispatch is missing.** The plan registers four tools but Task 3 names only registration, `tool_choice`, and logging (`docs/plans/2026-11-05-discord-voices-lookups.md:76-77`). `callClaude` ignores `tu.name` and passes every tool's `input.query` to `searchEverything` (`scripts/mags-discord-bot.js:523-542`). Input `lookup_neighborhood({name:"KONO"})` therefore becomes an empty search, and all four lookups can silently return `(empty search)` while the bot answers. Dispatch by tool name with validated per-tool arguments, an explicit unknown-tool result, and one result per `tool_use_id` is required.

- **F2 — FIX, `any` does not preserve the research.30 first-search contract.** The present forced named tool guarantees the disk + Supermemory + article-index fan-out (`scripts/mags-discord-bot.js:478-489,501-505,523-525`); the proposed `any` permits a first call to any one of five tools and the loop accepts multiple tool uses in that round (`scripts/mags-discord-bot.js:528-543`; `docs/plans/2026-11-05-discord-voices-lookups.md:65`). For `Oaks record`, `lookup_business` is a plausible but wrong first choice because `Business_Ledger` has `Oakland Oaks` (`output/beats/Business_Ledger.jsonl:70`); it would skip the sports feed and published context. Decide whether the invariant is *one search_world fan-out first* or *one relevant record lookup first*, and test ambiguous names and multiple first-round calls against that contract. Prompt wording alone cannot enforce the selected source.

- **F3 — HOLD, the acceptance ranking cannot follow from the proposed sort.** `searchDisk` ranks the ledger at 0, editions/archive at 1, and `output/beats` at 3, then takes only the top `maxFiles` (`lib/mags.js:665-674,723-745`); the bot asks for eight (`scripts/mags-discord-bot.js:481-483`). Sorting **within** a rank by Cycle cannot move the C114 Vinnie sports-feed file above rank-1 older editions, so the plan's “feed in the first three disk lines” acceptance case remains unproved and can still be impossible (`docs/plans/2026-11-05-discord-voices-lookups.md:63,84`). Give a query-matched current feed row an explicit ranking rule or prove the record lookup, separately, surfaces it.

- **F4 — FIX, a JSONL file hit is not a row hit.** The existing exact-phrase/AND fallback selects *files*: later terms may occur in different lines (`lib/mags.js:684-716`). Picking the “newest matching row by Cycle” without reapplying the same phrase/AND test to each row can serve a latest row unrelated to the query; reapplying it without defining the file-level fallback can turn a prior file hit into an unexplained absence (`docs/plans/2026-11-05-discord-voices-lookups.md:63,75`). Preserve exact-phrase-first behavior, define row-level matching for JSONL, and retain all relevant same-Cycle rows where the event log contains more than one event.

- **F5 — FIX, an all-terms *line* loses valid text-shelf hits.** `searchDisk` intentionally AND-matches whole files for markdown/text, then displays one matching line (`lib/mags.js:680-716,741-752`). The plan's “line matching every term” rule (`docs/plans/2026-11-05-discord-voices-lookups.md:63`) can produce no snippet for a valid article whose name is on one line and the queried event on another. Keep the file match and show a bounded excerpt around the best hit, or show separate matched lines with source line numbers; do not turn a multi-line record into “not found.”

- **F6 — FIX, the proposed ledger Name gate discards valid ledger queries.** The snapshot deliberately synthesizes `Name` while retaining `POPID` and every other ledger field (`scripts/dumpLedger.js:15-24,67-70`). Requiring a query term in `Name` (`docs/plans/2026-11-05-discord-voices-lookups.md:63`) drops `POP-00001` and role/status/hood searches whose answer is in a row but whose query has no name token. It also lets a common name token admit a row where the other terms occur elsewhere. Require an exact POPID or resolved name for person lookups; keep field searches on the generic `search_world` path with row-level relevance and identity checks.

- **F7 — FIX, not every JSONL shelf has a `Cycle` field.** `Neighborhood_Demographics` has `LastUpdated`, `Business_Ledger` has neither `Cycle` nor `LastUpdated`, and the ledger snapshot is a stable file with a separate stamp (`output/beats/Neighborhood_Demographics.jsonl:20`; `output/beats/Business_Ledger.jsonl:5`; `scripts/dumpLedger.js:21-34`). A generic “newest matching row by Cycle” comparator (`docs/plans/2026-11-05-discord-voices-lookups.md:63,75`) yields missing/NaN order or discards the only current row. Use each shelf's actual schema and `output/beats/meta.json` or `simulation_ledger_snapshot.meta.json` for snapshot freshness; require the dump stamp before labelling a record current (`scripts/dumpBeatTabs.js:22-29`; `scripts/buildEconomicSlice.js:109-133`).

- **F8 — HOLD, a full name does not identify one citizen.** The design promises `lookup_citizen(name or POPID)` returns “one record” (`docs/plans/2026-11-05-discord-voices-lookups.md:58`). The current snapshot contains two `Jacob Perez` rows, `POP-00203` and `POP-01089` (`output/simulation_ledger_snapshot.jsonl:155,916`). Taking the first name match would join one person's ledger row to another person's card or first-person page. Resolve to a unique POPID or return disambiguation before fetching the page/card/feed.

- **F9 — FIX, a citizen page is a first-person memory stream, not a current fact row.** `recentPage_` lists a remote container and GETs raw documents in created-time order, without query relevance (`lib/citizenPage.js:239-280`); the present voice only reads its *own* page and fences the content, skipping show records (`lib/personaProvider.js:429-455`). The proposed arbitrary-person lookup would present those reflections beside a ledger row as “newest facts” (`docs/plans/2026-11-05-discord-voices-lookups.md:54,58`). Label them as that citizen's recollections, preserve type filtering and fencing, handle `{error}` as unavailable, and do not let their creation time override a current ledger fact.

- **F10 — FIX, raw sick-count rank does not establish a rising illness spike.** The plan has KONO 17, Chinatown 137 and calls the latter the neighbor “that does have the spike” (`docs/plans/2026-11-05-discord-voices-lookups.md:46,59,85`). The health reader defines a spike by `Sick / (Students+Adults+Seniors)` at or above 6%, or 25% above the prior Cycle (`scripts/buildHealthSlice.js:36-60`). The C114 rows give KONO 17/537 and Chinatown 137/2213; C113 Chinatown was 140/2201 (`output/beats/Neighborhood_Demographics.jsonl:11,20`; `output/beats/prev/Neighborhood_Demographics.jsonl:11,20`). Chinatown is above the watch bar and highest by count, but its count **fell**. Return count rank, share/watch status, and prior-Cycle movement as distinct facts; never infer worsening from rank.

- **F11 — HOLD, census rows require system, Cycle, scope, intake type, and completeness together.** `Care_Justice_Census` contains neighborhood, unallocated and city rows, each with typed events and an `all` aggregate; the established reader filters Cycle + System + `IntakeType=all`, keeps scopes separate, and withholds numbers when `Completeness` is not `complete` (`scripts/beatSliceKit.js:497-529`). A broad “current-cycle hospital + judicial all rows” read (`docs/plans/2026-11-05-discord-voices-lookups.md:59`) can give KONO the citywide admissions or double-count typed rows with `all`; treating `TotalIntakes` as people currently in care also confuses arrivals with `ClosingOccupancy` (`scripts/beatSliceKit.js:535-558`). Require the exact neighborhood key and scope, expose admissions versus closing occupancy separately, and surface incomplete/missing census as unavailable.

- **F12 — FIX, the latest sports-feed row need not have a usable team record.** The plan reads the newest row's `Team Record`/`Streak`/`WeekRecord` (`docs/plans/2026-11-05-discord-voices-lookups.md:60,91`). The C114 A's tail is rumors, front-office, and player features with `Team Record: "-"`, `Streak: "-"`, and blank `WeekRecord` (`output/beats/Oakland_Sports_Feed.jsonl:255-259`); a C114 Oaks game-result has `6-1`, `W2`, `H:W` (`output/beats/Oakland_Sports_Feed.jsonl:265`). The contract requires a record for `game-result`, but not for every event (`scripts/sportsFeedContract.js:300-312`). Filter by exact team and usable record-bearing event, retain season type and Cycle, and say “no current record on this feed” when none exists. `WeekRecord` encodes ordered home/away game outcomes, not another W-L standings field (`utilities/sportsWeekRecord.js:2-23`).

- **F13 — HOLD, TrueSource `asRoster` is neither an A's-only roster nor proof that Oaks people are absent.** Its producer selects **all** `ClockMode=GAME` citizens and maps ledger `RoleType` into the TrueSource `position` field, without a team-membership field (`scripts/buildDeskPackets.js:275-314,623-632`). The local TrueSource reference includes Oaks-marked Adash Stanley and Dillon Brooks (`output/desk-packets/truesource_reference.json:393-398,442-447`); `Business_Ledger` also names both franchises (`output/beats/Business_Ledger.jsonl:5,70`). The plan's “A's roster from truesource” and “No Oaks roster exists” (`docs/plans/2026-11-05-discord-voices-lookups.md:60`) can report an Oaks citizen as an A's player or deny an Oaks-associated citizen. Treat this as GAME-mode people with role text, not a verified club roster; derive membership only from an explicit team source.

- **F14 — HOLD, business absence can mean closure, while a card can remain.** `Business_Ledger` is the active table; the engine copies a closed business to `Business_Archive`, verifies the copy, then deletes its active row (`phase05-citizens/applyBusinessDynamics.js:780-786,839-856`). `wdCardsDaemon` detects changed IDs but does not dispatch deleted IDs (`scripts/wdCardsDaemon.js:168-174`). Thus a name-only ledger/card lookup (`docs/plans/2026-11-05-discord-voices-lookups.md:61`) can either report a closed business as current from a surviving card or say an established closed business never existed. Resolve by `BIZ_ID`, distinguish active ledger from archive with `ExitCycle`/`ClosedCycle`, and treat the card as secondary context.

- **F15 — FIX, `metadata.cycle` is not universal card metadata.** The plan says v3 results carry `metadata.cycle` and orders all canon hits by it (`docs/plans/2026-11-05-discord-voices-lookups.md:13,54,76`). Saturday Tribune documents write `cycle` (`scripts/cron-saturday-run.js:272-284`), but citizen, neighborhood, and business cards write IDs/title/source without a Cycle (`scripts/buildCitizenCards.js:232-241`; `scripts/buildNeighborhoodCards.js:241-251`; `scripts/buildBusinessCards.js:161-170`). Sorting those cards as if they had a Cycle leaves relevance order or an undefined tie; `updatedAt` is a write timestamp, not an in-world Cycle. `lib/supermemory.search` returns raw results while `searchContext` strips metadata (`lib/supermemory.js:70-73,95-102`), so use the raw path for typed metadata, verify exact card ID/tag, and give Cycle-less cards an explicit undated secondary position.

- **F16 — FIX, the proposed brief sentence makes an unsupported chronology claim.** `buildVoiceBrief_` reads the ledger first and sports-feed lines second (`lib/personaProvider.js:263-282`); the plan would assert that the feed is newer whenever it differs (`docs/plans/2026-11-05-discord-voices-lookups.md:67,78`). Both local snapshots are C114, while the feed says “stepping away” and the ledger still says `Active` (`output/beats/Oakland_Sports_Feed.jsonl:258`; `output/simulation_ledger_snapshot.jsonl:1`). Those facts can coexist: an announced departure is not necessarily a completed status transition, and the feed's event Cycle alone does not timestamp it after the ledger dump. Show “C114 feed reports stepping away; C114 ledger still says Active” until a dated status transition is on record.
