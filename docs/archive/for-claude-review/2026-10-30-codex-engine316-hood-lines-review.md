# engine.316 — adversarial review of `6b0732f4`

**Verdict: HOLD.** The pool repair itself reaches the intended empty directions, but Baylight's lines claim places in use that the saved initiative state does not establish, and the proposed bench acceptance can print a clean ending with zero new lines. ## Findings

### F1 — Baylight place state is ahead of its initiative state (HOLD)

`phase05-citizens/runNeighborhoodEngine.js:225-230` adds lines about lights in more *new units*, strollers on *new blocks*, and a *waterfront walk* that is “usually busy.” On a Baylight growth or decay roll, `:601-613` can select these as observations and `:716-739` writes them into the citizen's LifeHistory and LifeHistory_Log. The saved `output/beats/Initiative_Tracker.jsonl:5` has INIT-006 at `construction-active`, with C113 Phase II remediation, dust control, and a C115 construction milestone review; its `OpensCycle` is blank. `docs/canon/INSTITUTIONS.md:353` describes the planned residential units and 1.2-mile promenade and says residents grow *as the build completes*. Neither record establishes occupied new units, walkable new blocks, or an open project waterfront walk at this point. Input: a moving Baylight week before the relevant opening → output: a signed citizen observation of a completed, used amenity. The plan's statement that these lines “assert no finished amenity” (`docs/plans/2026-10-10-engine-214-mood-per-hood.md:376`) is not supported by the current tracker. Bind each claimed existing place to an open/pre-existing source, or use observations that do not require an opened project place.

### F2 — the bench can declare success with zero drafted lines (HOLD)

`output/engine-sheet/2026-10-30-e316-check.js:17,29-35` reads `fromCycle` but never filters `LifeHistory_Log` by it; it only prints `hits` and `wrong`, and exits 0 even when `hits=0` or `wrong>0`. It also compares a historical log line against the citizen's *current* `Simulation_Ledger.Neighborhood` (`:24-33`), although the queued log row contains the neighborhood at write time (`phase05-citizens/runNeighborhoodEngine.js:724-735`); a later move can manufacture a false wrong-hood result or mask one. The wrapper pipes the checker to `grep` and then unconditionally restores and prints `engine.316 bench done` (`output/engine-sheet/2026-10-30-e316-bench.sh:29-32`); it has `set -uo pipefail` without `-e` (`:6`). Input: both fires PASS but no drafted line lands after the start Cycle, or the checker errors → output: a zero-hit/error report followed by a successful-looking completion. Require positive, Cycle-filtered hits, zero wrong-hood rows against the log's own neighborhood, and an explicit nonzero gate in the wrapper. The saved log (`output/engine-sheet/2026-10-30-e316-bench.log:1-8`) only shows the stage-34 push/pullback and propagation wait; it does not contain two fire verdicts, drafted-line counts, or restoration.

The saved push receipt does show `6b0732f4` as the supplied candidate (`output/engine-sheet/2026-10-30-e316-bench.log:1-4`); this finding concerns repeatability of the tool, not a claim that this particular push used the wrong source.
