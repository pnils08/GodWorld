# engine.317 read-only admission door review — 2026-10-30 (codex)

**Verdict: HOLD for the current candidate and PROD gate.** The normal `action=admission` path does not fire a Cycle or write state, and the saved sandbox bench passed. The error path can return `ok:true` with an error and a diagnostic unrelated to the admission record; equal read/fire tokens collapse the intended capability split; and the reader's `valid` flag is weaker than the engine's record check. No PROD admission-door read or guarded push is evidenced here. Engine-sheet can settle these findings in the allowed re-review round.

## Findings

1. **HOLD — an admission read failure returns false success and can expose persistence diagnostics.** The branch sets `out.ok = true` *before* reading `FIRE_ADMISSION_PROP` (`utilities/webTrigger.js:43-50`); the shared catch sets `error` without resetting `ok` and conditionally attaches `ENGINE95_PERSIST_DIAG` (`:93-98`). Input: a valid read token and a throwing admission-property read while that global diagnostic is non-null. Output: `{ok:true,error:"property read failed",persist:{...}}` with no admission, even though the read key was meant to receive only the fire record. I reproduced that response in a pure local VM; `ENGINE95_PERSIST_DIAG` can contain executor error details (`phase01-config/godWorldEngine2.js:1032-1043`). A normal script invocation may initialize the global to null; this is a reachable branch condition, not evidence of a PROD leak. `2026-10-30-e317-door.js` rejects the missing admission despite `ok:true` (`output/engine-sheet/2026-10-30-e317-door.js:20-27`), but an `ok`-only caller would accept it. Keep the admission branch's error response closed and free of fire diagnostics.

2. **HOLD — equal token properties make the read key a fire and POST key.** The admission branch accepts either property (`utilities/webTrigger.js:43-49`); a non-admission GET compares the supplied string with `CYCLE_TRIGGER_TOKEN` and reaches `runWorldCycle` with `expect` (`:51-64`), while POST uses that same fire-token comparison (`:119-127`). Input: `ADMISSION_READ_TOKEN = CYCLE_TRIGGER_TOKEN = "same"`, then `?token=same&expect=<current cycleCount>` with no admission action. Output: a Cycle fires. A pure local VM exercised that exact combination. It also confirmed that missing/empty keys refuse, a read-only key with no fire token reads but cannot fire, and distinct keys preserve the split. The task's earlier PROD probe reports no fire token; I made no PROD call to recheck it. The rollout must keep the keys distinct and verify that PROD's fire token remains absent before treating the read key as a read-only credential. With equal keys, POST's whitelist and bench-only reconciliation actions are also authenticated by that string (`utilities/webTrigger.js:128-193`).

3. **SHIP-WITH-FIXES — the door reader's `valid` check omits a writer invariant and HTTP success.** Its state list matches `FIRE_STATES` exactly, and it enforces integer cycle/time and finished-time rules (`output/engine-sheet/2026-10-30-e317-door.js:16-25`; `phase01-config/godWorldEngine2.js:305-310`). But the writer rejects `startedMs > now + 5 minutes` (`godWorldEngine2.js:235,308`), whereas the door accepts such a record; it also exits 0 for a valid-looking JSON body regardless of HTTP status (`2026-10-30-e317-door.js:18-27`). Input: a future-dated `done` record, or a non-200 response containing `{ok:true,admission:<valid-looking raw>}`. Output: `valid:true`/exit 0 when the engine would refuse the record or the HTTP read did not succeed. This is a validator mismatch, not an observed bench failure. Require HTTP 200 and the writer's clock bound before a push script relies on `valid`.

4. **PROD gate HOLD — the door exists, but the saved push gate still never reads it.** The existing PROD push script checks sheet counters, `_CycleCheckpoint`, `Engine_Errors`, and intake/ledger surfaces at its checkpoints (`output/engine-sheet/2026-10-30-push-r31-prod.sh:36-90`), while an admission is written as `running` before the Cycle body or Sheet writes (`phase01-config/godWorldEngine2.js:343-349`). Input: a C-next admission that aborts before the sheet counters move and leaves no durable error row. Output: the old sheet-side gate can print the next Cycle "not fired" although `FIRE_ADMISSION_JSON` changed. A new push gate needs authenticated reads from the **same pinned PROD script project** before the push, after pullback, and after the watch; each must have HTTP 200, a valid complete record with the expected baseline Cycle and `done` state, and unchanged `cycle`, `startedMs`, `state`, and full raw record. Reject missing, malformed, `running`, `checkpointed`, any new Cycle, or any change; keep the Sheet checks. The door helper's hardcoded PROD deployment ID matches this checkout's `.clasp.json` (`output/engine-sheet/2026-10-30-e317-door.js:7-12`; `.clasp.json:2-3`), but a live deployment listing, version/pullback binding, token provisioning, and fresh PROD reads remain unverified in this review.
