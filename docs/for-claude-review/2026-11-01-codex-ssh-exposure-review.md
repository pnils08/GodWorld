# SSH exposure review — 2026-11-01

**Verdict: HOLD the proposed address rule.** I cannot establish that someone other than the owner got in, and I cannot clear the server as owner-only. The retained logs show 15 successful root-password logins from three public addresses outside the proposed ranges. The owner must identify those sessions. Today, anyone on the internet can try the root password; fail2ban slows repeated guessing but does not prevent a login with a known password. The smallest durable fix is to confirm that the owner's saved Chromebook connection can use an owner-controlled SSH key, test that login and a recovery route, and then turn off SSH password login everywhere. If the owner does not recognize any successful session, treat it as possible root compromise, not just a firewall problem.

## 1. Who got in?

They contain 598 successful SSH authentications: 596 root passwords and two root public-key uses, from 18 distinct source IPs (one is this server's own public address). They also contain 55,444 failed password attempts, including 25,839 against root. An accepted login proves valid authentication, not the person's identity. A Chicago-area source is not identity evidence.

I checked login-shell accounts (`/etc/passwd`: only root), root's crontab, `/etc/cron*` names, running process names, running systemd services, and `pm2 list`. I found no clearly foreign account, cron entry, service name, or running process in those checks. This is limited evidence: a root intruder could remove traces, and I did not inspect every file or every command run inside prior SSH sessions.

## 2. Exposure and real risk

- Effective `sshd -T` says `permitrootlogin yes`, `passwordauthentication yes`, `pubkeyauthentication yes`, and `kbdinteractiveauthentication no`. `/etc/ssh/sshd_config:42` explicitly allows root. `/etc/ssh/sshd_config.d/50-cloud-init.conf:1` enables passwords before `/etc/ssh/sshd_config.d/60-cloudimg-settings.conf:1` tries to disable them; the effective setting is **yes**.
- `ss -tlnp` shows sshd listening on `0.0.0.0:22` and `[::]:22`. `ufw status verbose` shows an active default-deny firewall, but it allows TCP 22 from **Anywhere** on IPv4 and IPv6. The server has a public IPv4 address, and the live auth log shows inbound password attempts. The IPv6 interface had no public IPv6 address in `ip -br addr`; I did not establish public IPv6 reachability.
- `fail2ban-client status sshd` showed 33,988 cumulative jail failures, 4,550 cumulative bans, and one IP banned at the check. It is operating, but it cannot stop a correct password used on the first try or from a source not yet banned. Successful root password use grants full control of this server. UFW also allows TCP 3032 from anywhere, though `ss -tlnp` showed no listener on 3032 at the check; that rule is separate from the SSH decision.

## 4. Candidate change

**HOLD.** The scratch file `sshd-candidate/d/00-godworld-password-limit.conf:1-3` is syntactically valid. I piped a read-only copy of the current main config with that candidate included before the existing drop-ins into `sshd -T -f /dev/stdin -C ...`; I did not install it. The resulting effective settings were: root password **yes** for `172.59.187.10`, `172.57.5.5`, `12.74.61.33`, and `108.147.98.49`; root password **no** for `76.150.103.144`, `99.190.68.156`, and the server's own `64.225.50.16`. Root public-key login stayed **yes** in all tested cases, and `PermitRootLogin` stayed **yes**. Thus the rule narrows password access as claimed; it does not confine all SSH access to those addresses.

The three CIDRs permit password attempts from 458,752 IPv4 addresses in total (`/14` + `/15` + `/16), far beyond one owner or device. It would reject password sign-ins from the three successful outside addresses above, from self-SSH via the public address, and from any future Chromebook address outside the ranges. Because the owner currently describes a password-based saved connection and cannot inventory all devices, applying this rule now has a concrete lockout risk. The tested key login is promising, but its ownership and availability on the owner's saved connection remain unverified. Global password-off after that verification has better security and simpler behavior.
