# engine.275 pre-PROD rereview — HOLD

Read-only review of `23341c87..f27f21fe` at `f27f21fe`. No deployment, live fire, Sheet read, or Sheet write. The sheet menu still binds `Run World Cycle` to `runWorldCycle` (`utilities/godWorldMenu.js:25-28`). The new VM test replaces the production body with a counter (`scripts/fireGuard.test.js:63-74`), so it does not exercise the real cache flush, counter repair, or AdvanceTime exception paths.

## Regression and live-fire walk

- **First sheet-menu fire after deploy, no record:** `readFireGuardConfig_` reads the sheet counter and guard (`godWorldEngine2.js:245-272`); `admitCycleFire_` skips prior-record checks and writes `running` (`:289-337`); the real body loads the same counter and advances once (`:492-500,866-883,891-925`). With successful cache and Spreadsheet flushes, close reads that Cycle and records `done` (`:823-842,416-426,377-398`). No normal first-fire blockage found. A missing guard key defaults to 60 and is seeded after admission (`:264,410-451`).
- **Next week's menu fire:** a correctly persisted first fire has advanced the sheet counter, so the proposed Cycle exceeds the prior record's Cycle (`:277-278,304-311`). The 60-minute check has expired (`:315-327`), and the new fire is admitted. A counter that *did not* persist is intentionally refused for the same Cycle until reconciled, regardless of elapsed time. The record shape written by this code is accepted on the next fire (`:294-297,395-396`).
- **Clean abort before AdvanceTime, then refire:** an unwrapped carry-forward check runs before AdvanceTime (`:493-500`). With no summary Cycle, close writes `aborted` (`:372-376,395-398`); the body exception is rethrown, the lock is released, and the next menu fire bypasses the prior-record and time tests for `aborted` (`:307,315`). This is safe only when the summary being unset really precedes counter queueing and world phases. Contract seeding can already have happened (`:433-452`), so “aborted” does not mean zero Sheet writes of any kind.
- **Type checks on a healthy run:** `loadConfig_` turns numeric text into a number via `parseFloat` (`:866-883`); the admission reader accepts numeric cells/text as numbers (`:255-272`); `assertFireConfigLoaded_` compares numeric values (`:344-350`). `advanceWorldTime_` computes a number and assigns it to `summary.cycleId` (`:907-915`), which `assertFireAdvanced_` compares numerically (`:352-357`). Neither check should throw for a stable, valid `cycleCount`; the AdvanceTime exception hole above remains.
- **Throwing after `finally`:** on a body exception the `catch` rethrows at `:413-415`, so the post-`finally` throws at `:424-427` are unreachable and do not replace that original error. On a normal body return, a close problem is logged at `:397` and then thrown to the menu/web caller at `:426`; counter-repair failure can also have logged at `:1016-1021`, yielding two `Engine_Errors` observations for one incident. If `closeCycleFire_` itself throws while the body already threw, `:420-421` suppresses the close error, preserving the body error but leaving closure failure unreported to the caller.
- **Lock ownership:** failed `tryLock` exits before the `try/finally` and owns no lock (`:404-409`). Every ordinary path after acquisition, including admission refusal, body throw, flush failure, and close failure, reaches `releaseLock()` (`:416-423`). A release exception is swallowed at `:422`; Apps Script documents automatic release at execution termination. The flush is attempted while the lock is still held. [Google Lock documentation](https://developers.google.com/apps-script/reference/lock/lock).
- **Close read-back and repair:** the body calls cache `flush()` and attempts the counter repair before returning (`:823-842,945-979`). Its pre-wrapper read may see a pending Spreadsheet write and attempt a redundant repair, but close performs its own read *after* `SpreadsheetApp.flush()` (`:416-422,377-393`). A successful final flush promises pending changes applied; on an ordinary healthy run this order does not mislabel a persisted counter `unpersisted`. A failed final flush is conservatively `unverified`, even if the counter read matches. [Google SpreadsheetApp.flush documentation](https://developers.google.com/apps-script/reference/spreadsheet/spreadsheet-app#flush).
- **New `doPost clearfire` regression:** `utilities/webTrigger.js:85-96` checks the token but deletes `FIRE_ADMISSION_JSON` without acquiring the engine lock, reading `World_Config`, requiring an expected record/Cycle, or restricting the action to the sandbox. A token-bearing POST can clear `running` or `done` during or after a fire; after a hard failure with an unchanged counter, that removes the same-Cycle refusal (`godWorldEngine2.js:289-311`). The plan says PROD currently has no trigger token (`docs/plans/2026-09-21-care-and-justice-system.md:647,659`), which closes that door for the stated PROD configuration, not for a later token-bearing deployment. Restrict reconciliation to a verified bench target, serialize it with the fire lock, and require an explicit expected record and Sheet-counter check.

## Validation and decision

`node scripts/fireGuard.test.js`: **98 passed, 1 failed**. The failed assertion `6b.16` cannot run `scripts/ctxMap.js` as a child in this sandbox (`spawnSync /bin/sh EPERM` at `scripts/ctxMap.js:21-24`); a read-only in-process run of the scanner with the same phase/utilities file list reported **161 orchestrated slots**. The VM's production body is stubbed (`scripts/fireGuard.test.js:63-74`), so its passing assertions do not close findings 2 or 3. No live Sheet or deployment proof was attempted.

**Verdict: HOLD before PROD.** Make failed AdvanceTime fatal even after summary assignment, carry known partial cache-commit failure into close, enforce the full record shape, and gate `clearfire` to a locked, verified bench reconciliation. Verify the plan's single-project PROD condition before relying on it.
