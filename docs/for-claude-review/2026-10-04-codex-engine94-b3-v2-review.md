# engine.94 B.3 revised cut v2 review

**Verdict: HOLD.** The builder's ruling settles the calendar-election question: turnover belongs in the every-Cycle approval writer, and both scheduled-election calls should go. V2 still cannot meet its retirement, persisted bond-ID, and one-fire bench acceptance as written. This is source review only; no sandbox or live Sheet was read or fired.

## Numbered findings

1. **Campaign outputs can retire, but the cleanup and tests cannot simply disappear (a, e).** A search over `phase*`, `utilities`, `scripts`, `lib`, `dashboard`, `.claude/agents`, `riley`, and `openclaw-skills` found no production reader of `S.civicCampaigns`, `S.officeDepartures`, or `S.approvalTriggers` outside their producer. The only exact `S.civicCampaigns` consumer is a test (`scripts/civicApprovalState.test.js:222`). The `[CAMPAIGN]` note *does* have a reader: `seedOccupiedPopIds_` reserves its POPID before every office is processed (`phase05-citizens/updateCivicApprovalRatings.js:522,1193-1213`). V2 must replace that reservation with holder-only occupancy plus same-pass successor reservation, and retain a one-time note-strip operation until legacy notes are gone; deleting `parseCampaignNote_` while leaving `seedOccupiedPopIds_` unchanged breaks the function. The current `CIVIC_CHALLENGER_CAMPAIGN` hook and `campaign` trigger are produced only in `:783-809`; generic story-hook carry and deck writing still handle other civic hooks (`phase07-evening-media/storyHook.js:1401-1426`; `phase08-v3-chicago/v3StoryHookWriter.js:68-98`). Retire the old G/H campaign assertions and source exports as well as B3 (`scripts/civicApprovalCeiling.test.js:35-40,311-459,644-694`). Removing the campaign hook changes historical output by design under the builder's no-campaign ruling; no exact downstream hook-type dependency was found in the searched surfaces.

2. **The no-challenger re-check is only conditionally idempotent (a, e).** Tier 3 appends an out-of-town `Generic_Citizens` row and returns null (`updateCivicApprovalRatings.js:1508-1549`). The next Cycle can find that active row and mint a ledger challenger (`:1434-1487,1552-1580`), so the intended single-seat retry works *after the append commits*. The marker check reads only the persisted GC sheet (`:1513-1525`); a repeated call before Phase 10 commits can queue a second arrival. More seriously, tier 2 never marks the GC row consumed: `mintChallengerOnLedger_` pushes a new ledger row (`:1379-1425`) while `pickGenericCitizenChallenger_` leaves the GC row active (`:1451-1487`). A second under-40 office can mint the same named GC person under another POPID, including in the same fire. Reserve/consume GC candidates per office and prove a two-seat retry and replay case. V2's phrase “nothing is persisted” should mean no *campaign or seat* state: the fallback deliberately queues a GC arrival, and approval/threshold writes may still occur (`:932-947,1002-1004`).

3. **Retirement/death needs an explicit branch before the status gate and a no-successor policy (b, e).** The current loop skips a vacant office and `resolveApprovalCeilingLifecycle_` blocks every status except active/recovering (`updateCivicApprovalRatings.js:285-326,535-574`). If an office row itself is `retired` or `deceased`, the approval/seating block is never reached. If v2 means the *holder's Simulation_Ledger row* is retired/deceased, it must resolve that POPID before approval and route the seat despite the office status; the plan does not say how. The same no-challenger rule would otherwise keep someone unable to serve in the chair while an arrival waits. Specify and test the temporary office state and voting power when no successor exists, then fill it on re-check. Existing vacant rows are also skipped (`:553-554`), so “vacant only when the ledger is missing” is not by itself a recovery path.

4. **Turnover must synchronize the citizen ledger (a, b, d).** The seating block writes only `Civic_Office_Ledger` Holder/PopId/VotingPower/approval/Notes (`updateCivicApprovalRatings.js:811-830,932-947`). The election path being deleted is the only reviewed turnover writer that marks a winner `CIV (y/n)=y`, sets a role, and dirties `ctx.ledger` (`runCivicElectionsv1.js:528-545`). `runCivicRoleEngine_` requires `CIV (y/n)=y` for civic events and reads `RoleType` when `TierRole` is absent (`phase05-citizens/runCivicRoleEngine.js:133-139,238-245`). V2 must update the successor by exact POPID in `ctx.ledger`, use the present role column, and define what happens to the displaced holder's CIV/role state. Otherwise the office ledger says one person holds the seat while the citizen engine still treats the predecessor as civic and the successor as non-civic. Test the two ledgers together, including retirement and board seats.

5. **The load flag belongs at the successful load boundary, but read success needs validation (c, e).** Both schedules run LoadBonds before ApprovalRatings and Bonds after it (`godWorldEngine2.js:587-625,2265-2303`). `bondExists_` can linear-scan before Bonds builds its key set, and `createBond_` appends to the same array (`phase05-citizens/bondEngine.js:1699-1717,2709-2737`). Resetting `S.relationshipBondsLoaded=false` at load entry and setting it true after a validated header-only or complete load is sound for the grudge guard: `loadRelationshipBonds_` clears the array, returns early on header-only, aborts on ledger-schema collision, then otherwise loads rows (`phase05-citizens/bondPersistence.js:111-177`). But it does **not** validate required master columns; missing `CitizenA`/`CitizenB` silently becomes blank (`:138-170`), while a separate validator already defines required headers (`utilities/ensureRelationshipBonds.js:234-278`). A flag set merely after `getValues()` would certify malformed data. A load exception is swallowed by `safePhaseCall_` (`godWorldEngine2.js:159-169`); guarding only this grudge also leaves later generic bond creation able to queue a partial master replacement (`bondEngine.js:267-309`; `bondPersistence.js:221-289`). Use a valid-schema load gate for this seed and prevent Phase 10 replacement after any failed master load.

6. **`grudgeBond` on the hook object will not persist or reach the civic desk (c, f).** V2 fixes the earlier transient-departure mistake by proposing `leaveHook.grudgeBond`, but `saveV3Hooks_` serializes exactly 14 named fields, with no bond ID (`phase08-v3-chicago/v3StoryHookWriter.js:32-46,68-98`). The civic domain slice reads `HookText`, `SuggestedAngle`, and `Neighborhood`, not arbitrary hook properties (`scripts/buildCivicDomainSlice.js:280-295`). The normal ripple writer also keeps only description/type/severity, not `grudgeBond` (`utilities/rippleLedger.js:100-118`). Thus a bench read-back of a `CIVIC_DEMOTION` hook *with* `grudgeBond` cannot pass. Either persist a structured BondId column and wire its reader/schema, or put the bond ID in `HookText`/description and test that exact read-back. Keep the in-memory property if useful, but do not call it a persisted handoff.

7. **Approval 30 does not guarantee a one-fire unseat (f).** V2 gates on **new** approval under 40 after initiative deltas and the city/press target pull (`updateCivicApprovalRatings.js:591-702`), not on the fixture's starting value. The seeded inertia is 0.2 (`phase01-config/engine94SheetContract.js:125-129`); target 95 alone moves 30 by `round((95-30)*0.2)=13`, to 43 (`updateCivicApprovalRatings.js:691-702`), and positive initiative motion can add more. A pre-confirmed qualified challenger solves candidate availability, not the threshold. Before firing, use a controlled fixture with a proved upper bound on the next approval or calculate/observe the post-score under 40; verify the actual selected challenger is distinct, eligible, and unbonded. Then read back the office, bond master and ledger, and persisted hook. A single fire proves the mechanism only under those preconditions.

8. **Deleting the election source is correct under the ruling, but v2's deletion list misses a live reader and more tests (d, e).** The only runtime calls found are the two scheduled calls (`godWorldEngine2.js:594,2272`); `S.electionResults` has no production reader in the searched surfaces. Historical `Election_Log` readers can remain (`phase10-persistence/buildCyclePacket.js:1472-1502`; `scripts/buildCivicDomainSlice.js:257-277`; `utilities/cycleRollback.js:55,276`). Yet `buildCyclePacket_` independently computes even-year election windows and “seats up” from `ElectionGroup`, then prints a next-election countdown (`phase10-persistence/buildCyclePacket.js:1399-1459,144-161`). Removing the engine without retiring that packet branch would publish a false scheduled election. Besides B3 and D1/D2, the test file loads election source at top level and D3 checks it (`scripts/civicApprovalCeiling.test.js:57-59,183-190`); `scripts/auditRemainingHeaders.contract.test.js:91-96` asserts the soon-retired `Election_Log` writer mapping. Reconcile these, `README.md:16`, `docs/engine/ENGINE_MAP.md:126`, `docs/SPREADSHEET.md:242`, and the stale election wording in the owning plan's B.4/live acceptance (`docs/plans/2026-07-31-citizen-memory-perception.md:272-275`). The civic.43 plan's live acceptance already reflects approval turnover (`docs/plans/2026-10-04-school-board.md:49`), although its older election description remains at `:29,63`.

## Disposition

Keep the no-scheduled-election, under-40 same-Cycle direction. Before implementation or bench, amend v2 for findings 2-8 and update the campaign tests/occupancy in finding 1. Tests must exercise the real `updateCivicApprovalRatings_` writer and read the persisted hook shape. No code, plan, Sheet, or `SESSION_CONTEXT.md` was changed; this report is the only artifact.
