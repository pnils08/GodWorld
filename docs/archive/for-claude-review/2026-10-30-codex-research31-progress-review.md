# research.31 progress scoring review — 2026-10-30 (codex)

**Verdict: HOLD** on `72395ec9`. The visible, stable-meter path pays a mark once across nights: a 10-point mark moving 0 → 0.5 → 1 pays 5 + 5, and the settle preserves those progress-scored nights. The paths below can instead lose earned progress, over-credit a retry, or publish a measured zero from an incomplete read. These are scoring-mechanism findings, not rulings on which actions deserve points.

## Findings

1. **HOLD — a newly visible or hidden unlock earns zero on a progress night.** `accountFrom` omits a hidden, unearned achievement from the before map (`scripts/undockedEpisodeAdapter.js:800-814`). `progressPoints` iterates the after map but skips IDs absent before (`:822-833`); `assemble` treats its `{value:0}` as a valid progress result and never calls the timestamped unlock fallback (`:397-403`). Input: a hidden 60-point mark is absent from the before map, then appears earned in the after map, with a valid `earned_at` inside the night. Output: `PointsDelta=0`; the unlock rule would yield 60. A visible achievement first returned after the before-read has the same gap. The new test keeps its hidden mark unearned on both reads (`scripts/undockedEpisodeAdapter.test.js:239-258`), so it misses this case. I reproduced the 0 versus 60 result with pure local `accountFrom`/`progressPoints`/`derivePoints` calls.

2. **HOLD — an old or wrong-pilot starting line can be accepted after a failed snapshot.** `snapshotProgress` writes one reusable file per session (`scripts/undockedEpisodeAdapter.js:564-570`), and cron catches a failed new snapshot then launches the flight (`scripts/cron-undocked-run.js:360-375`). `beforeSnapshot` checks only the file timestamp and presence of `account`; it never checks `snap.session`, account identity, or that this launch produced the file (`scripts/undockedEpisodeAdapter.js:554-561`). Input: an attempt starts at fraction 0.2, moves a 10-point mark to 0.5, and fails before staging; a retry starts within 30 minutes, its new snapshot fails, and the mark reaches 0.6. Output: the retry uses 0.2 as its baseline and gets 4 points for its own 0.1 movement, instead of 1. A copied snapshot for another pilot at the expected path also passes if its timestamp is in range. The normal producer names the file for its requested session; the failure is in accepting a leftover or mismatched file without a launch/identity binding.

3. **HOLD — incomplete meter data becomes measured zero.** `readAccount` requires an achievements array but no complete meter set (`scripts/undockedEpisodeAdapter.js:773-777`). The earned-total reconciliation does not validate unearned meters (`:785-814`); a visible mark with a blank or malformed `progress.current` is silently assigned fraction 0 (`:138-140,807-812`). `progressPoints` then returns a non-null zero if no positive difference survives, and `assemble` publishes it (`:822-833,397-403`). Input: before-read has a 10-point mark at 2/10; after-read has the same earned total but its current meter is blank. Output: `PointsDelta=0` with `basis:progress`, despite the unreadable after meter. An after response omitting all unearned marks while keeping the same earned total also passes and scores zero. A transport error in the after request does take the unknown/fallback path (`:542-545`); this finding is the successful but incomplete response path. I reproduced the blank-current zero with pure local calls.

4. **HOLD — per-night quantization loses cumulative board points.** `progressPoints` drops gains at or below `0.0001`, rounds each item and the night's total to two decimals (`scripts/undockedEpisodeAdapter.js:826-833`), and the board sums those already rounded `PointsDelta` values (`scripts/undockedStandings.js:93-101,132-137`). Input: a 40-point mark moves by fraction 0.0001 on each of three nights. Each night has a real 0.004-point gain, but records 0; the board shows 0 after all three rather than the 0.012-point cumulative gain (or 0.01 if only the display is rounded). The saved local account snapshot contains fractions as small as 0.000001 (`output/spacemolt-show/progress/undocked-pop00734.json:175-178`), so fine-grained meters are a present input shape, though it is not a before/after flight pair. I reproduced three 0-valued nights with pure local calls. Even a single gain below 0.0001 is discarded before rounding.

5. **HOLD — a delayed unlock can be frozen out permanently.** Cron waits 180 seconds after the runner exits, then makes the after-read (`scripts/cron-undocked-run.js:377-387`). A progress-scored fact is kept verbatim on every later points settle, although the settle has a 15-minute arrival window for unlocks (`scripts/undockedEpisodeAdapter.js:265-285,912-916`). Input: a visible 10-point mark is at fraction 0.5 before and at the after-read; its unlock appears 181 seconds after flight end, within the 15-minute attribution window. Output: the after-read records 0 and later settlement keeps 0, instead of the remaining 5. The source comments report an observed 2.9-minute arrival lag (`scripts/undockedEpisodeAdapter.js:265`; `scripts/cron-undocked-run.js:381-383`), leaving a narrow margin; I did not verify a later live unlock. A later account read cannot repair this path as written.

## Source wiring and limits

Cron takes the preflight snapshot, runs the flight, then waits and invokes the adapter (`scripts/cron-undocked-run.js:356-387`). The adapter projects `facts.points_delta`; the gate appends approved `PointsDelta` to `Undocked_Feed` (`scripts/undockedEpisodeAdapter.js:397-404`; `scripts/undockedShowGate.js:279-314`). `undockedStandings.compute` sums that column into rank and its sidecar (`scripts/undockedStandings.js:62-101,132-141,201-213`); phase02 separately sums aired feed rows into `S.undockedBoard` (`phase02-world-state/loadEventContentLedger.js:315-325,363-410`). The required Haiku `engine-wiring` call for `Undocked_Feed PointsDelta progress scoring` was attempted once and returned `[FATAL] Connection error.`; this is a source-derived wiring card, not a generated one.

The normal visible-meter completion case does **not** double-count its unlock: `earned` changes its fraction to 1 (`scripts/undockedEpisodeAdapter.js:807-812`), `progressPoints` pays only the difference (`:826-833`), and later settlement keeps that night's fact (`:912-916`). An actual after-request error yields unknown (`:542-545,274-277,397-403`). `UNDOCKED-BRIEF/5` explains the board's progress rule with a scoring example and leaves the pilot free to fly; I found no new route instruction in its changed text (`scripts/undockedMissionBrief.js:60-65`). Its claim that `get_achievements` shows *every* achievement is broader than the adapter's handling of hidden unearned marks (`:63`; `scripts/undockedEpisodeAdapter.js:800-814`).
