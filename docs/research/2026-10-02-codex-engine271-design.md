# engine.271 design review — HOLD

Scope: the plan's `### engine.271 read-before and design` through **Build shape** and **Bench proof**, checked against the named implementation. This is a mechanism review; the builder's simulation choices stand. Source inspection only: no live Sheet, bench, or deployment proof. The shared worktree changed during inspection: engine.271 config, treasury, judicial, and ticket code is now partially implemented and dirty. References below describe the source observed on 2026-10-02, including those uncommitted edits. The plan still says “not built,” so neither its live C109 counts nor the current partial code should be treated as a landed build.

## Twelve checks

1. **Treasury facts — mixed.** **CONFIRMED:** `City_Treasury` is an append-only six-column ledger in this engine; Phase 2 queues `OPENING`, `PREFUNDED`, allocation `REVENUE`, `APPROPRIATION`, and `RENEWAL`, with `BalanceAfter` captured from the current balance (`phase02-world-state/applyInitiativeImplementationEffects.js:290-326`, `:428-445`, `:470-476`, `:1017-1049`). `readTreasuryLedger_` takes the latest finite balance and remembers appropriated counterparties (`:1031-1049`). **CONTRADICTED:** “one REVENUE per Cycle” is only the allocation guard; new court/ticket/tax posts are also `REVENUE`. The current guard keys only `WEEKLY-ALLOCATION` by Cycle and stops when *any* `PROPERTY-TAX` row exists (`:319-326`, `:1044-1047`). “S.treasury has no reader” is stale: `postTreasuryRevenue_` reads and advances it (`:1118-1129`). “Nothing takes a fine today” and “chaosCarsEngine never touches NetWorth” are stale against the dirty partial implementation (`phase05-citizens/judicialLifecycle.js:453-492`, `phase04-events/chaosCarsEngine.js:48-63`, `:400-422`). The live tab's “headers, no rows” cannot be verified from source. **Fault:** the ledger reader does not validate required headers or malformed balances; a blank `BalanceAfter` is accepted as numeric zero and a missing header yields a negative index (`applyInitiativeImplementationEffects.js:1033-1042`). The allocation guard must use its own counterparty, as the current partial edit does, but a zero-collection first tax day produces no `PROPERTY-TAX` row through the proposed amount-positive post helper and therefore never ends allocation (`:1047`, `:1118-1129`).

2. **Phase-10 order — mixed.** **CONFIRMED, conditionally:** Phase-2 treasury rows and the current `postTreasuryRevenue_` both queue at priority 5 (`applyInitiativeImplementationEffects.js:815-819`, `:1124-1128`). `queueAppendIntent_` places them in `ctx.persist.updates` (`utilities/writeIntents.js:147-161`). Phase 10 sorts updates by numeric priority, groups by **sheet**, then batches each sheet's appends in the surviving order; it does not order by domain (`phase10-persistence/persistenceExecutor.js:74-86`, `:127-145`, `:348-360`, `:399-442`, `:463-472`). At equal priority, JavaScript's stable sort preserves queue order; a later post at default priority 100 also follows priority-5 Phase-2 rows. **CONTRADICTED:** “all append intents execute in queue order” is false across priorities; merely queuing in Phase 4/5 is insufficient if a later post uses a lower priority. “BalanceAfter stays monotone” is false literally: appropriations and renewals decrease it (`applyInitiativeImplementationEffects.js:432-435`, `:473-476`). What must hold is row-by-row balance continuity. Fix the treasury writer's priority contract and test mixed priorities, multiple posts, and debits.

3. **Treasury presence and failed Phase 2 — CONTRADICTED.** A tab alone does not set `S.treasury`: the function returns before treasury initialization when `Initiative_Tracker` is missing or has no data rows (`applyInitiativeImplementationEffects.js:226-247`), and only publishes `S.treasury` at its end (`:813-820`). `safePhaseCall_` logs and continues after a throw (`phase01-config/godWorldEngine2.js:159-169`, `:529-563`, `:2225-2255`). A later citizen charge can therefore happen while `postTreasuryRevenue_` silently returns null, leaving no matching city receipt (`applyInitiativeImplementationEffects.js:1118-1129`). The current comment explicitly accepts that loss (`:1112-1117`). Treasury initialization must be independent of the initiative tracker, and a failed treasury phase must make revenue unavailable explicitly, with a recoverable receipt or a fail-loud gate before charging.

4. **Demand handoff — mixed.** **CONFIRMED:** Phase 4 constructs each hood's `judicialIntakes = round(charges × clearance)`, `ratePopulation = hood table share × city population`, and `trackedResidents` from non-excluded ledger rows (`phase04-events/careJusticeService.js:105-133`, `:173-220`). It publishes the completed object only at the end and deletes a previous value first (`:136-147`, `:236-241`). Both entry points run demand before Chaos Cars, Judicial, and GenerationalWealth (`phase01-config/godWorldEngine2.js:562-625`, `:2250-2321`). **CONTRADICTED:** “already carries, every Cycle” is not guaranteed: a failed demand phase is swallowed by `safePhaseCall_`; no `S.careJusticeDemand` then exists. The current court helper silently returns zero when it is absent (`phase05-citizens/judicialLifecycle.js:500-505`); the multiplier helper returns an empty map (`applyInitiativeImplementationEffects.js:1137-1150`). The build must verify demand's current-Cycle stamp, complete hood set, finite values, and positive multiplier denominator, and report/stop city receipts on failure. Zero measured demand is different from unavailable demand.

5. **Named fine and case closure — mixed, with a blocking replay gap.** **CONFIRMED:** the normal outcomes are `released`, `diverted`, `held-served`, and investigation `no-arrest`; held is an intermediate state, then closes as `held-served` (`phase05-citizens/judicialLifecycle.js:45-85`). Death/trade/inactivity make reconciliation outcomes (`:617-623`). A resolved case is not advanced again *once the case row is durable* (`:257-261`, `:286-315`). `Income` and `NetWorth` headers are required, but an individual Income cell may be blank/non-numeric/zero; `Number(...) || 0` then yields no fine even as the case closes (`:553-557`, `:468-471`). **CONTRADICTED:** copying the lost-pay `[IncomeHit J<ArrestCycle>]` marker is not a durable replay guarantee. Both that marker and the new `[Fine J<ArrestCycle>]` marker live in `LifeHistory`, whose compressor retains only the last 20 raw entries (`utilities/compressLifeHistory.js:58-77`, `:675`, `:1100-1135`). The fine marker is checked only in that cell (`judicialLifecycle.js:472-475`). The 21-field case and exact 21-column Phase-10 writer contain no `Fine` (`judicialLifecycle.js:36-40`, `phase10-persistence/buildCyclePacket.js:1260-1277`, `:1308-1357`). Thus the design's “new Fine column” and Build shape's “no new column” conflict; current code records no fine on the case. A failed case write with citizen write succeeding can re-close and recharge after the marker is trimmed; a successful case write with citizen write failing can close without a paid fine forever. Use a durable case-linked fine receipt/amount and explicit reconciliation of the two writes; resolve the column/schema conflict in the build spec. Keep the ruled exemptions for reconcile, minors, GAME clock, and released cases (`judicialLifecycle.js:459-469`).

6. **Tickets and the money loop — mixed.** **CONFIRMED:** the event writer uses the shared `ctx.ledger.rows[target.rowIndex]`; the dirty partial implementation can read `Income`, `NetWorth`, and `DebtLevel` there and debit that row (`phase04-events/chaosCarsEngine.js:50-63`, `:395-422`). `processMoneyLoop_` later reads `row[iNW]` from the same shared rows (`phase05-citizens/generationalWealthEngine.js:370-411`, `phase01-config/godWorldEngine2.js:563-625`), so it sees the Phase-4 debit; later accrual and home purchase change that *updated* value, rather than restoring an old Sheet snapshot (`generationalWealthEngine.js:424-426`, `:519-522`, `:1870-1874`). **CONTRADICTED:** eligibility does not prevent every minor from receiving a ticket event: the `ticket` outcome gate permits age 16–17 and unknown age, while `parking_ticket` has no outcome gate; `pickCitizenTarget_` has no age or ClockMode filter (`chaosCarsEngine.js:140-163`, `:201-245`; `utilities/chaosCarsConfig.js:294-300`). GAME-clock citizens can also receive the event. The proposed charge may skip minors/GAME, as current code attempts, but the event still exists. Missing columns, unreadable NetWorth, or failed post must be surfaced without claiming the fine was collected. The current ticket path can debit before posting and catches later errors (`chaosCarsEngine.js:405-418`), which needs receipt reconciliation.

7. **Property-tax pass and engine.276 — mixed.** **CONFIRMED:** `trackHomeOwnership_` reads `Household_Ledger` directly, indexes `Members` JSON to current `ctx.ledger` rows, checks active rented households, and includes living members in the purchase's net-worth split (`phase05-citizens/generationalWealthEngine.js:1797-1855`, `:1870-1874`). The home price is `max(S.neighborhoodState[hood].medianRent, ownRent) × 12 × 22`; missing hood median falls back to own rent (`:1774-1778`, `:1857-1862`). Calendar sets `S.cycleOfYear = ((absoluteCycle-1) % 52)+1` before Phase 5 when `Simulation_Calendar` exists (`phase01-config/advanceSimulationCalendar.js:34-55`, `:178-180`; `godWorldEngine2.js:513`, `:2209`). **CONTRADICTED:** owned households do not *necessarily* have a real mortgage in `MonthlyRent`: new purchases write an estimated payment there, but the home model has no loan balance and seeded owned homes can lack `HousingCost` (`generationalWealthEngine.js:1895-1898`, `:1922-1938`). The tax pass needs the active owned household's hood and adult members, not a borrowed assumption from the rented-only purchase loop; it must define missing/duplicate/non-adult member behavior, validate market price, and use a consistent household snapshot. The planned pass after `processMoneyLoop_` means that Cycle's debt lean/default and the pre-loop `WealthLevel` will not reflect tax until a later update; a pass after `trackHomeOwnership_` also taxes homes purchased on tax day. These ordering effects need explicit checks (`generationalWealthEngine.js:146-193`, `:401-508`, `:1857-1898`). Engine.276's purchase gate and conditional default/home rolls can change as a result.

8. **Carry test — CONFIRMED with required wiring.** `homeCarries_(mortgageMonthly, householdIncome)` currently checks mortgage annualized against 30% of income (`phase05-citizens/generationalWealthEngine.js:1791-1795`). Its **two** callers are initial purchase (`:1857-1867`) and trade-up planning (`:2060-2079`). Annual tax needs the actual price and configured rate at both calls, or the trade-up door stays easier than a first purchase. Test both paths at the 30% boundary.

9. **Eleven dials and self-arm — mixed.** **CONFIRMED:** the dirty partial build already defines eleven seeds and calls `ensureEngine271Config_` before cache creation on the real fire (`phase01-config/engine94SheetContract.js:313-344`, `phase01-config/godWorldEngine2.js:439-473`); the shared inspector validates headers, duplicate keys, finite bounded values, and integer keys, preserving operator values (`engine94SheetContract.js:482-523`). **CONTRADICTED:** the design's “missing key throws where read” is not guaranteed by the current `cityRevenueConfig_`: `Number('')` and `Number(null)` become zero, and it checks only `isNaN`, not finiteness or bounds (`applyInitiativeImplementationEffects.js:1062-1075`). The self-arm is absent from dry-run/replay entry points (only the real wrapper calls it; `godWorldEngine2.js:439-462`, `:2189-2199`). Specify a strict runtime reader and tests for blank/malformed/missing values; keep tax-day position and thin-floor integer bounds. Also define a durable first-tax-day marker even when tax collections are zero, since a positive-only post cannot switch off the allocation (`applyInitiativeImplementationEffects.js:321`, `:1047`, `:1118-1129`).

10. **Determinism — mixed.** **CONFIRMED:** the new fine and tax arithmetic requires no new RNG call (`applyInitiativeImplementationEffects.js:1079-1089`, `:1137-1150`). **CONTRADICTED:** “no other engine's draws move” does not follow. The pre-Phase-5 ticket and named debits change net worth and debt before the money loop's conditional default draw (`phase04-events/chaosCarsEngine.js:400-413`, `phase05-citizens/judicialLifecycle.js:635-642`, `phase05-citizens/generationalWealthEngine.js:415-419`, `:491-498`). Tax and annual carry change who passes the purchase gate, and its RNG draw is conditional (`generationalWealthEngine.js:1857-1867`); future Cycles' default and purchase draws can also shift. No new draw site is different from an unchanged draw stream. Bench proof should use invariants and draw-count/draw-order instrumentation, not assume byte-identical replay against old code.

11. **Money conservation and retries — CONTRADICTED as a complete contract.** The plan says city court revenue is **all** hood cleared charges **plus** named fines; a tracked arrest belongs to the hood charge set, so this counts it twice unless the two sets are made disjoint (`phase04-events/careJusticeService.js:203-223`, plan engine.271 Finding 2/Design 2). The current dirty helper subtracts tracked intake **on arrest Cycle** but adds the named fine **on closure Cycle**; a tracked release then produces neither named fine nor that hood charge, and a closure after a failed intake/case write needs a stable bridge (`phase05-citizens/judicialLifecycle.js:500-514`, `:573-590`, `:659-667`). The builder's source and unscaled named amount can both stand with explicit disjoint accounting. Citizen `NetWorth` is clamped to zero and Phase-2 appropriations/renewals draw at most the treasury balance, so these paths do not make those balances negative (`applyInitiativeImplementationEffects.js:432-435`, `:473-476`, `:1048-1052`, `:1096-1109`). But a shortfall still credits the *full* nominal fine or tax while only the citizen's available savings are subtracted and debt rises one ordinal level; there is no dollar liability or cash receipt for the gap (`:1096-1109`, `judicialLifecycle.js:470-492`). State whether the row is assessed or collected revenue and make its amount agree with that basis. `postTreasuryRevenue_` has no event key or tab readback (`applyInitiativeImplementationEffects.js:1118-1129`); the Phase-10 batch appender retries at the current tail and clears intents after reporting errors (`phase10-persistence/persistenceExecutor.js:176-179`, `:399-449`). A partially landed/failed write has no receipt-level replay protection. Use stable event IDs and readback/reconciliation for named fine, ticket, tax day, and treasury posts.

12. **Numbers — mixed.** **CONFIRMED arithmetically:** 29.4 × $4.4K ≈ $130K; $130K × 52 ≈ $6.76M; $9.2B × 1% = $92M; 386,587 / 918 ≈ 421 and 421 × $1,065,986 ≈ $449M; C120 has year position 16 (`phase01-config/advanceSimulationCalendar.js:48-55`). **CONTRADICTED/unsupported as code-derived proof:** the section says both **169** and **176** businesses; it never defines the discrepancy. `judicialIntakes` is rounded **per hood**, so “29.4 cleared a Cycle” is a pre-round modeled expectation, not the posted integer count (`phase04-events/careJusticeService.js:203-223`). The $130K court row also depends on 22 different hood medians and caps, not just that 29.4 total (`phase05-citizens/judicialLifecycle.js:500-514`). The $279M/$315M property totals, 124 owners, 918 tracked, and “all 124 pay” require the cited live C109 rows and an explicit adult/hood/rounding calculation; they cannot be derived from these functions. Current per-household and final treasury rounding can change totals (`generationalWealthEngine.js:1857-1874`, `applyInitiativeImplementationEffects.js:300-301`, `:1118-1127`). Treat those as estimates until source-traced Sheet/bench readback; require exact ledger totals in bench checks rather than approximate totals alone. A no-error-row expectation cannot be unconditional when demand/config/treasury failures are deliberately logged by phase handling (`godWorldEngine2.js:159-169`).

## Verdict and required changes

**HOLD.** The builder's rulings are implementable, but the current design and partial worktree do not yet specify a replay-safe, auditable revenue mechanism.

1. Initialize/validate treasury independently of `Initiative_Tracker`; fail loud or retain a durable pending receipt when a citizen is charged but treasury posting is unavailable. Validate ledger headers, balances, and row-by-row continuity.
2. Define exact treasury append priority and replay identity; make the allocation stop on the first tax day even if collections are zero, with a durable tax-day receipt. Prove ordering with mixed-priority and partial-write cases.
3. Make current-Cycle `careJusticeDemand` required for court and property scaling; distinguish zero from unavailable, validate hood coverage and denominators, and stop the city post on invalid input.
4. Resolve the `Judicial_Ledger.Fine` versus “no new column” conflict. Persist fine amount and case-linked payment identity; reconcile case closure, citizen debit, and treasury receipt across failures and LifeHistory trimming. Define missing/unreadable Income handling before closure.
5. Make hood court charges and tracked named receipts disjoint with consistent opening/closure timing, preserving the ruled hood-charge source and unscaled named fines. State and test whether treasury amounts are assessed or actually collected when savings fall short.
6. Implement the property pass from active owned households with validated adult members and market price; specify its ordering against the money loop and same-Cycle purchases, and cover seeded owned households. Thread annual tax through **both** home carry callers.
7. Strictly validate all eleven dials at read time and the real-fire self-arm; show dry-run/replay preconditions. Instrument conditional existing RNG draws rather than claim unchanged draw order.
8. Replace the approximate bench-only claims with row-level reconciliation: per-citizen debit and case/ticket identity, per-hood scaled tax math, exact treasury `BalanceAfter` continuity, one tax-day marker, allocation absent thereafter, and retry/readback checks. Reconcile the 169/176 business count and source-trace the C109 baselines.
