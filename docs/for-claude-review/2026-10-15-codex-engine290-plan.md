# engine.290 transit plan — Codex source review

Scope: current checkout and local C111 dumps only. No Cycle, Sheet, bench, cron, model, or canon run. Gates below judge whether each plan move is ready for implementation; they do not claim runtime proof. Doctrine §§1–8 require causes before dice, ledger-backed people, and honest canon output (`docs/SIM_DOCTRINE.md:19-67`).

## 1. Write boundary — SHIP

`recordTransitMetrics_` uses `metrics.onTimePerformance || 0.85` and `metrics.trafficIndex || 50` (`utilities/ensureTransitMetrics.js:417-430`); the batch writer repeats both at `:449-468`. Station calculation emits `trafficIndex: 0`, corridor calculation emits `onTimePerformance: 0` (`phase02-world-state/updateTransitMetrics.js:461-470,566-573`). The plan's blank-by-row-kind fix addresses the real coercion.

No named reader averages OTP or TrafficIndex across both row kinds: the slice separates stations and corridors before numeric reads and totals station ridership only (`scripts/buildTransitSlice.js:34-60`); the auditor checks row presence (`scripts/engineAuditor.js:74-84`); the header auditor checks column names (`scripts/auditRemainingHeaders.js:77-84`). The dashboard maps every row and turns a blank into 0 (`dashboard/server.js:1590-1602`); civic packets filter to station rows and `parseNum('')` also becomes 0 (`scripts/buildCivicVoicePackets.js:72-75,403-413`). These do not crash or alter an average, but their API/packet representation remains numeric zero for N/A. `scripts/beatSlices.test.js:37-47,228-236` still fixtures the old pseudo-values; update the fixture when move 1 lands.

## 2. Clocks and RNG — FIX

Both engine entry points run Phase1-Calendar before Phase2-Transit (`phase01-config/godWorldEngine2.js:558,585,2275,2302`). Calendar sets all four requested fields (`phase01-config/advanceSimulationCalendar.js:187-197`). The intervening Phase 2 steps read them; no assignment to those `S.` fields appears in `phase02-world-state/` (the reads include `applySeasonWeights.js:29-40` and `applyCityDynamics.js:169-174`). CityDynamics and commute flows also precede Transit at both entries (`godWorldEngine2.js:580-585,2297-2302`).

The plan must specify how its holiday cut and corridor traffic interact with the existing day-type branches (`utilities/ensureTransitMetrics.js:506-512`; `phase02-world-state/updateTransitMetrics.js:530-535`), and define the First Friday station mapping: no station's served-hood list contains `KONO` or `Uptown` (`utilities/ensureTransitMetrics.js:37-98`), although the plan promises those hoods a station lift (`docs/plans/2026-10-15-engine-290-transit-rides-the-sim.md:44`). A literal hood-intersection implementation would lift only the Downtown stations.

`safeRand_` returns the shared `ctx.rng` (`utilities/safeRand.js:28-35`). Removing transit's private weekend draw and breakdown draw (`phase02-world-state/updateTransitMetrics.js:127,233`) first changes the station ridership/OTP and corridor variance draws (`:444-459,562-564`), then every downstream consumer of that stream. The affected output families are Phase 3 demographics, crisis spikes, crime, and hood demographics (`godWorldEngine2.js:590-595`); Phase 4 world/faith/chaos events (`:602-608`); Phase 5 citizen micro/game/civic/media events, relationships/bonds, careers, education, household, generational/justice/youth, Intake, citizen events, and promotions (`:617-670`); Phase 6 economy/migration/texture (`:695-707`); Phase 7 city/nightlife/sports/food/fame/media and contract seeds (`:736-755`); Phase 8 neighborhood writer (`:772-796`); and Phase 10 event IDs/recording where RNG is used (`:814-823`). Direct RNG-owning source files include `phase03-population/applyDemographicDrift.js:42`, `generateCrisisSpikes.js:54`, `updateCrimeMetrics.js:194`, `updateNeighborhoodDemographics.js:31`; `phase04-events/worldEventsEngine.js:56`, `faithEventsEngine.js:83`, `chaosCarsEngine.js:865-890`; `phase05-citizens/generateCitizensEvents.js:466`, `runCareerEngine.js:56`, `bondEngine.js:15`, `generationalWealthEngine.js:37`, `processAdvancementIntake.js:781`; `phase06-analysis/economicRippleEngine.js:185`, `applyMigrationDrift.js:14`; `phase07-evening-media/buildNightLife.js:44`, `buildEveningFood.js:37`, `buildEveningFamous.js:54`, `buildEveningMedia.js:40`, `sportsStreaming.js:29`, `textureTriggers.js:15`, `buildContractSeeds.js:194`; and `phase10-persistence/recordWorldEventsv3.js:44`. These are possible changed outputs, not independent regressions; the plan's whole-Cycle non-pairability warning is correct (`plan:55`).

## 3. Ridership share — HOLD

The local `Neighborhood_Demographics` C111 dump has 22 rows and 31,398 Adults, ranging from 411 to 2,286 (`output/beats/Neighborhood_Demographics.jsonl:1-22`); the loader reads `Adults` as hood counts (`utilities/ensureNeighborhoodDemographics.js:134-165`). `S.commuteInbound` is a count of tracked workers, summed from `ctx.ledger` rows (`phase02-world-state/commuteFlowEngine.js:15-19,139-160,196-217`), so it is on the 1:443 sample scale (`docs/SIM_DOCTRINE.md:40-43`). An inbound/adults ratio without a common scale makes the work-hood signal tiny; the plan never defines `inboundRatio(h)`, its scale conversion, or the bounded `retailTerm(h)` (`plan:45,64`). `retailVitality` is a prior Neighborhood_Map numeric read (`phase02-world-state/loadNeighborhoodState.js:105-124`); it is not guaranteed 0–10—source records C96 range 6.6–15.1 (`phase08-v3-chicago/v3NeighborhoodWriter.js:76-80`). `S.neighborhoodDynamics[h].traffic` is a 0.3–3.0 multiplier, not an index in 0–100 (`phase02-world-state/applyCityDynamics.js:250,311-320,1542-1551,1847`). A corridor/city mean ratio is dimensionally sound if missing/zero cases are defined.

The station `corridors` lists include `Coliseum`, `Elmhurst`, `North Oakland`, and `Montclair`, which have no C111 demographic row (`utilities/ensureTransitMetrics.js:66-97`; `output/beats/Neighborhood_Demographics.jsonl:1-22`). `Adams Point` and `Piedmont Ave` **do** have rows (`Neighborhood_Demographics.jsonl:8,10`), contrary to the task's example. The ten traffic corridors' `hoods` are all present in that dump (`utilities/ensureTransitMetrics.js:128-208`). The existing commute engine folds Coliseum/Elmhurst to East Oakland via `resolveHoodOrChild_` (`phase02-world-state/commuteFlowEngine.js:125-132`); the proposed station share does not say whether to resolve, exclude, or give a real station fallback to each missing name. Mixed `base: table` stations and ledger-share stations would also stop the shares summing to 1 unless the fallback and normalization are specified. Define that algorithm and test all eight stations with the actual 22-hood set before cutting.

The promised `rebased` Factor is insufficient on its own: `scripts/buildTransitSlice.js:27-45,57-80,87-96` still prints prior-Cycle deltas and labels the largest one as a ridership move; it never reads `rebased`. The plan must change and test the slice, including the lead label and total comparison, or the C112 repair will be reported as a city event (`plan:45,56,76-77`).

## 4. Crew — HOLD

`ctx.ledger` is loaded before Phase 1 (`phase01-config/godWorldEngine2.js:538-558`; `phase01-config/initSimulationLedger.js:37-53`). `RoleType`, `Status`, and `EmployerBizId` are present in the local snapshot (`output/simulation_ledger_snapshot.jsonl:456,870`; also `phase02-world-state/commuteFlowEngine.js:139-145`). At BIZ-00014 the local roster/snapshot has only POP-00617 Eleanor Rivera, `BART Station Manager`, Active, and POP-01039 Ximena Mehta, `Bart Transit PR`, Active (`output/beats/Employment_Roster.jsonl:490,853`). The five proposed regexes classify Eleanor as `stationManager` and Ximena as none; conductor/operator/dispatcher/maintenance are all zero. That supports governor default 0.

`Status !== Active` is too broad for a named absence: the lifecycle includes hospitalized, critical, recovering, injured, serious-condition, detained, retired, deceased, and others (`phase04-events/generationalEventsEngine.js:97-125,420-441`; `phase05-citizens/runCareerEngine.js:273-313`). Care and custody also have explicit Hospital_Ledger/Judicial_Ledger states (`utilities/careJusticeAccounting.js:29-35,408-414`). Restrict the named cause to an actual active-to-care/custody transition or open receipt, with prior employer/role still held; a retired or departed historical crew row is not a temporary shortage.

The plan's same-Cycle acceptance is impossible at the chosen phase: transit runs Phase 2, while health/justice status transitions and career dismissal run Phase 4/5 (`godWorldEngine2.js:585,608,643,647-648,656`; `runCareerEngine.js:245-363`). A Phase 2 ledger read can first react on the next Cycle, and a Phase 5 recovery could erase a brief status before then. State the lag and test the exact persistent case, or add a later writer with explicit ownership. Do not claim the same-Cycle causal loop (`plan:46,65,79`).

## 5. Chaos carry — HOLD

`finalizeCycleState_` explicitly selects carry fields (`phase09-digest/finalizeCycleState.js:47-50,169-195`), so adding `S.chaosTransit` there is necessary. The previous-cycle blob is already described as about 8.2 KB against a 9 KB PropertiesService value cap (`:503-507`). An extra compact object may fit, but source alone cannot prove that in a full Cycle; `saveCarryForwardBlob_` falls back to the `Carry_Forward_Store` ring when the property refuses (`phase01-config/loadPreviousEvening.js:125-141`). Check serialized size on bench and gate consumption on `previousCycleState.cycle === currentCycle - 1`; the loader accepts any older stamped property (`:159-169`).

`pickNeighborhoodTarget_` chooses from all Neighborhood_Map names with one RNG draw and accepts no vehicle argument (`phase04-events/chaosCarsEngine.js:320-337,648-656`). A vehicle-specific filter can preserve one target draw for existing vehicles, but the plan must wire it through `pickTargetByScope_` and separately filter `pickCitizenTarget_`, which currently picks any eligible ledger citizen (`:205-225,648-656`). Otherwise a BART citizen hit can occur outside every served hood. `runChaosEvent_` writes one source row per hit and there may be multiple hits per Cycle (`:659-712,883-890`); a single `S.chaosTransit` object needs a defined collision rule, especially when `clean_run` follows a delay. `transitChaosWeight` also needs picker plumbing: `chaosLoopWeight_` reads only `vehicle.baseFrequencyWeight` and takes no `ctx` (`:108-129`).

`validateVehicleConfig` checks outcome strings only for forbidden death tokens (`utilities/chaosCarsConfig.js:77-92`); it does **not** reject an unknown `delay` field. `validateAllChaosConfigs_` checks per-scope weights and known metric-impact columns (`:383-448`); the proposed six outcomes still need numeric/range validation for `delay`, non-citizen weights summing to 1, and real `lifeHistoryTag` values on citizen outcomes. The local validator alone cannot prove the delay contract.

## 6. ECL flag — HOLD

A bare flag is parsed only if registered in `CONTENT_LEDGER_DSL_FIELDS` (`phase02-world-state/loadEventContentLedger.js:64-79,132-145`), and its truth is read as `scopes[t.f]` (`phase05-citizens/generateCitizensEvents.js:1070-1076`). `condScopes` is built per citizen in Phase 5 (`:2851-2883`), after Phase 2 transit has published `S.transitState` (`phase01-config/godWorldEngine2.js:585,656`; `phase02-world-state/updateTransitMetrics.js:230-263`). The flag needs a producer in `condScopes` as well as the loader registration; `source:occupation` is already whitelisted (`loadEventContentLedger.js:41-51`).

The stated eligibility and probability are **not equivalent** to today's code. Today's inline gate admits working citizens in affected hoods at 0.30 and working citizens elsewhere at 0.12, then offers **one** randomly chosen line at weight 1.15 (`generateCitizensEvents.js:2821-2834`). The proposed `transitdisrupted` flag admits only affected hoods (unless `affectedHoods` is empty) and then puts four-plus authored lines in the general weighted pool with no 0.30/0.12 Bernoulli gate (`plan:48,67`; `generateCitizensEvents.js:2926-2950,3163-3168`). Its per-row 40-draw cap further changes mass (`:2933-2939`). The old `if` at `:2826-2828` cannot simply “stay as the entry point” after its inline pool is removed; `condScopes` lives in another block. Specify whether the broader 0.12 city exposure is intentionally removed, and give the new odds/weight test. A hood-free conductor line also needs an employer/role criterion; the existing `occupation` scope is exact RoleType text (`generateCitizensEvents.js:318-325,2238-2240,2879-2883`; `loadEventContentLedger.js:79-82`).

## 7. Hiring plumbing — FIX

Matching is case-sensitive, first substring wins (`phase05-citizens/processAdvancementIntake.js:1546-1554,1609-1617`). Current `BART` maps prefixed Intake titles to BIZ-00014 before `Transit Hub` maps to BIZ-00096 (`:1558-1561,1583`); plain `Train Conductor`, `Train Operator`, `Rail Dispatcher`, `Transit Dispatcher`, and `Track Maintenance` match neither earlier rule and need the proposed additions. The JSON mapping has the same ordering (`data/employer_mapping.json:36-56,358`). The local economic catalog already has `Transit Dispatcher` (`data/economic_parameters.json:381`).

`SETTLE_ROLES_BY_FIELD['Transit & Infrastructure']` exists, but holds only `rich: Smart Grid Trainee`, `solid: Transit Operator Trainee`, `rough: Station Attendant` (`phase05-citizens/educationCareerEngine.js:893-899`). `runCareerEngine_` chooses exactly one role per one of those three education bands, only for a cross-field hire (`phase05-citizens/runCareerEngine.js:1741-1759`); it cannot “carry four titles” or guarantee conductor/dispatcher/maintenance through routine hiring without a specified role-selection change. Also a named BIZ mapping is conditional on field and `hasRoom(named)`, after which the picker falls back to field/hood or UNTRACKED (`processAdvancementIntake.js:1633-1658`); the plan's “any of five titles lands at BIZ-00014” acceptance needs a room/field fixture and an explicit decision on no-room behavior (`plan:82`).

## 8. Sequencing and canon writes — FIX

`World_Config` is cached and loaded into `ctx.config` at each Cycle start (`phase01-config/godWorldEngine2.js:917-933`), so a validated governor value can be changed for the next fire without another deploy. The engine.94 seed helper validates and self-arms missing rows before config load (`phase01-config/engine94SheetContract.js:598-650,717-749`; `godWorldEngine2.js:484-548`). Keep its exact fourteen engine.94 keys intact (`engine94SheetContract.js:15-31`) and give engine.290 its own seed list/helper in that file, as the existing engine.133 pattern does (`:33-46`).

The plan explicitly requires canon writes **besides** bench and code deploy: seeded World_Config rows on first fire; the builder's four Advancement_Intake1 mints; additive Event_Content_Ledger rows on PROD; and the later PROD `transitStaffingGovernor` cell flip (`plan:51-55,67,69-70`). These need a concrete order and post-write read-back before the next live fire. The governor-at-zero order is correct, but the plan's “after mints” check says only `dumpLedger.js` shows four BIZ-00014 rows (`plan:53`); source requires checking their Status and role classification too before arming (hunt 4). The `rebased` slice and ECL odds issues above must be fixed before any PROD sequence can be called safe.

Disposition: HOLD — revise moves 2–8 for the source-proven gaps above, then repeat a bounded plan review before engine-sheet builds or writes canon.
