# Dial fixes: source approval, separate data-repair gate

## Hunt 1 — SHIP the guard and producer; clock guarantee is conditional

- `utilities/compressLifeHistory.js:368,550–566` excludes a stamped entry beyond the current absolute Cycle before watermark admission. It counts existing future watermarks without lowering them. `:747,763` exposes both counts. This prevents new poisoning; it does **not** unfreeze an already-poisoned row. Those rows can still settle mood or receive other state updates; “frozen” describes objective-history admission, not every dial writer.
- Normal runner: `phase01-config/godWorldEngine2.js:550–559,807` validates the admitted clock, advances it, computes the calendar, then reaches Phase 9. `advanceWorldTime_` at `:943–977` sets both `summary.cycleId` and `config.cycleCount` to the absolute counter (dry-run retains it). `phase01-config/advanceSimulationCalendar.js:48–55,178` stores that counter in `S.absoluteCycle`, separately from cycle-of-year. No intervening production assignment replacing `S.absoluteCycle` with cycle-of-year was found.
- Second runner: `godWorldEngine2.js:2274–2276,2516` has the same advance/calendar/compress ordering. Thus **both successful initialization paths supply the absolute Cycle**. “Always” is too strong: this runner uses safe phase wrappers without the normal runner's `assertFireAdvanced_`; missing World_Config makes AdvanceTime return (`:945–946`), and calendar has a fallback of 1. The compressor also fails open when both clock fields are absent/zero. F1–F4 do not prove malformed-clock or failed-initialization safety. A fail-closed positive-integer clock check would be separate hardening, not a demonstrated valid-run regression in this guard.
- No legitimate producer requiring a future-stamped *completed* LifeHistory event was found in the searched engine writers. Household events use `ctx.config.cycleCount` (`phase05-citizens/householdFormationEngine.js:149,213–221`); milestone/birth history uses the current `cycle` (`phase04-events/generationalEventsEngine.js:1182,1722–1734`). Scheduling/carry is not evidence that its eventual history entry should accrue before occurrence. This is a bounded source-search conclusion, not proof over arbitrary imported text. The guard leaves text in the history-processing stream; it is not a durable scheduled-event queue and does not promise future text survives normal compression.
- Producer: `scripts/migrations/engine57_spouse_backfill.js:26,187` now derives year/cycle from **101**, yielding **Y2C49**, instead of the old Y3C29 (=133). Correct for the original mint; do not rerun the migration to repair existing marriages.
- **Parent falsification verified.** Running the new test file against `113e78aa^` utility sources: F1 fails (`folded=133`, drive mood=8); F2 fails (family mood=5); F3 throws because `futureStamped` is absent, so the unmodified suite never reaches F4. An independent F4 probe with a telemetry-safe lookup fails on the parent and passes on 113e78aa. Against 113e78aa, the full file reports **58 passed, 0 failed**, including F1–F4 (`scripts/compressLifeHistory.dial.test.js:332–355`). These are real discriminating assertions, not tests that passed unchanged before the fix.
- The commit also rolls back the prior unreviewed extra-key carry-through in citizenMemory/compressor serialization. That is explicitly in its commit message; this verdict does not imply arbitrary unknown DialState keys are now preserved.
